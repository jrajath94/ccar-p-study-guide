Your API key is the front door

Rung 1: the plainest version. Your API key is a password that buys Claude answers. You show it with every request; Anthropic bills your account for what you use.

  You ---(API key + question)---> Claude API ---(answer)---> You
                                          |
                                     bills your account

Rung 2: where the key lives. The key looks like sk-ant-.... It lives in an environment variable, never in code, never in git. The SDK picks it up on its own.

  .env file  -->  ANTHROPIC_API_KEY=sk-ant-...
                                          |
  your code: client = Anthropic()  <-------+
        |  (SDK reads the variable itself)
        v
  request header: x-api-key: sk-ant-...

import os
from anthropic import Anthropic

# The SDK reads ANTHROPIC_API_KEY from the environment automatically.
# Put the key in a .env file or your shell profile, never in source code.
client = Anthropic()

Rung 3: the full picture. A leaked key lets anyone spend your money, so you rotate it at console.anthropic.com the moment you suspect exposure. And enterprise teams sometimes skip the direct API entirely, calling Claude through AWS Bedrock or Google Vertex AI with IAM roles instead of an Anthropic key. Same request shape, different front door. The exam cares that you know both paths exist.

  Path A (direct):      you -- API key --> console.anthropic.com --> Claude
  Path B (enterprise):  you -- IAM role --> AWS Bedrock / Vertex AI --> Claude
Where does your API key live, and why?

In an environment variable (ANTHROPIC_API_KEY), loaded by the SDK. Never in source code or git, because a leaked key lets anyone bill your account.

Your first API call: the Messages API

Rung 1: the plainest version. You send a request with three things (which model, how long the reply may be, and your messages). You get back the reply text, why it stopped, and how many tokens it cost.

  REQUEST                              RESPONSE
  { model, max_tokens, messages }  -->  { text, stop_reason, usage }

message = client.messages.create(
    model="claude-sonnet-5",   # which model answers; family ids track the latest snapshot
    max_tokens=1024,           # required: a hard cap on the reply length in tokens
    messages=[
        {"role": "user", "content": "Explain prompt caching in one sentence."}
    ],
)

print(message.content[0].text)  # the reply text lives in the first content block
print(message.stop_reason)      # "end_turn" means Claude finished normally
print(message.usage.input_tokens, message.usage.output_tokens)

Rung 2: the four rules of the road. The API is stateless: it remembers nothing between calls, so every request stands alone. Messages alternate user, assistant, user, assistant (two same-role messages in a row get merged, not rejected, but do not rely on that). There is no system role: system instructions are a top-level parameter, covered next unit. And the prefill trick: if the last message has role assistant, Claude continues writing from that text instead of starting fresh, which is how you steer exact formats like JSON.

  messages = [
    {"role": "user",      "content": "Summarize:"},   \
    {"role": "assistant", "content": "Sure:"},         } alternating turns
    {"role": "user",      "content": "the report"},   /
    {"role": "assistant", "content": "{"},            <-- prefill: Claude completes the JSON
  ]
  system = ...   <-- top-level parameter, NOT a message

Rung 3: reading the response like a production engineer. content is a list of blocks (text, tool_use, thinking). stop_reason tells you why it stopped: end_turn (finished), max_tokens (hit your cap, answer may be cut), tool_use (wants to call a tool: next units), stop_sequence (hit your custom stop string). usage carries the token counts you need for cost tracking. The API accepts up to 100,000 messages per request; you will never hit that, because in practice you manage context yourself.

  stop_reason = "end_turn"      --> done, use the text
  stop_reason = "max_tokens"    --> answer may be truncated, raise the cap or chunk the task
  stop_reason = "tool_use"      --> run the tool loop (see the tool-use unit)
  stop_reason = "stop_sequence" --> Claude stopped at your custom marker, as designed
Speed:

Watch: freeCodeCamp's "Learn Claude AI" walks through getting a key, making first calls, prompt engineering basics, and error handling with real code. Note: it was filmed in 2024, so the model names it mentions (Claude 3.5 Sonnet) are dated, but the API mechanics are still current. Transcript vetted September 2026.

Which three parameters does every messages.create call require?

model, max_tokens, and messages. Everything else (system, tools, temperature, caching) is optional.

System prompts: the rules behind the curtain

Rung 1: the plainest version. A system prompt is the job description you hand Claude before the user ever speaks: who it is, the rules it always follows, the exact output format.

  +---------------------------+
  | SYSTEM: job description   |  <-- read first, applies to every turn
  +---------------------------+
  | user: ...                 |
  | assistant: ...            |
  +---------------------------+

message = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    # Top-level system parameter. Not a message, so it never appears
    # in the user/assistant turn sequence.
    system="You are a release-notes writer. One bullet per change. No adjectives.",
    messages=[
        {"role": "user", "content": "v2.4: fixed retry backoff, added SSO login"}
    ],
)

Rung 2: two shapes, two kinds of content. A plain string works for simple instructions. A list of blocks enables per-block controls like prompt caching (you will see cache_control sit on a system block in the caching unit). And content splits two ways: the stable contract (persona, rules, format) belongs in system; anything that changes per request (dates, user names, request ids) belongs in messages.

  system = [
    {"type": "text", "text": "You are a release-notes writer."},   \
    {"type": "text", "text": LONG_STYLE_GUIDE},  # can carry cache_control  } stable: cached
  ]
  messages = [
    {"role": "user", "content": "Today is 2026-09-28, user Ada..."},  <-- volatile: never cached
  ]

Rung 3: the production rule. Volatile content in the system prompt changes the prefix on every call and silently kills your cache hit rate. System holds the stable contract so its prefix stays cacheable; messages hold the changing facts. Get this split right and caching (a later unit) works almost for free.

  STABLE (system, cached)            VOLATILE (messages, fresh each call)
  - who Claude is                    - timestamps, user identity
  - permanent rules                  - the actual question or data
  - output format                    - tool results from this turn
The system-prompt trap

Putting per-request data (dates, user names, request ids) in the system prompt. It feels tidy, but it changes the prefix on every call and silently kills your cache hit rate. System holds the stable contract; messages hold the changing facts.

System prompt or message: where does today's date go?

In messages. The system prompt holds stable instructions only, so its prefix stays cacheable.

Multi-turn: you are the memory

Rung 1: the plainest version. The API is stateless, so a "conversation" is just you resending the history plus the new turn. Your app owns the messages array.

  Turn 1:  [ user: "hi" ]                                  --> reply A
  Turn 2:  [ user: "hi", assistant: A, user: "thanks" ]     --> reply B
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
           you rebuild and resend the whole array every turn

# Your app builds this array. The API never stores it for you.
conversation = [
    {"role": "user", "content": "My order 48151623 arrived damaged."},
    {"role": "assistant", "content": "I am sorry to hear that. Can you describe the damage?"},
    {"role": "user", "content": "The screen is cracked along the left edge."},
]

reply = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    system="You are a support agent. Be brief and empathetic.",
    messages=conversation,  # full history, every time
)

# After the call, append the reply so the next turn includes it:
conversation.append({"role": "assistant", "content": reply.content[0].text})

Rung 2: two consequences. First, cost grows with history: every turn resends every earlier token as input, so turn 50 costs far more than turn 1. Second, the prefill trick: end the array with an assistant message and Claude continues it, which is the cleanest way to force JSON output.

  input tokens per turn:  |##        turn 1: cheap
                          |########  turn 10: the whole history, resent
                          |################ turn 50: expensive

  prefill: [..., {"role": "assistant", "content": "{"}]  --> Claude completes the JSON object

Rung 3: the production fix. Long conversations need compaction: summarize old turns into one block, or keep only a recent window. Tool results also travel here: tool_result blocks ride inside user-role messages in this same array (you will write that loop in the tool-use unit).

  turns 1-40  -->  [summary block: "customer reported cracked screen..."]
  turns 41-50 -->  kept verbatim
  result: one compact array, bounded cost, no lost context that matters
Why does turn 50 of a chat cost more than turn 1?

Because the API is stateless: you resend the whole history every turn, so input tokens grow with conversation length.

Sampling parameters: temperature, top_p, top_k

Rung 1: the plainest version. Temperature is a dial from 0.0 to 1.0 on randomness (default 1.0). At 0, Claude almost always picks the most likely token: deterministic and reproducible. Near 1, it samples freely: varied and creative.

  0.0 ------------------------- 1.0
  predictable                     creative
  "the same answer every run"     "a different take each run"

Rung 2: the other two dials. top_p (nucleus sampling) samples from the smallest token set whose combined probability passes top_p. top_k cuts candidates to the K most likely tokens. In practice you tune temperature or top_p, not both at once.

  all tokens, ranked by probability
  [ the | a | an | this | that | ... ]
       <-top_k=3->                 <-top_p=0.9->
       keep 3 tokens               keep tokens until 90% probability mass

Rung 3: the rules of thumb, plus the 5.x caution. Classification, extraction, JSON, anything graded: temperature=0. Brainstorming and copy: 0.7 to 1.0. And on the 5.x generation, which uses adaptive thinking, leave sampling at defaults unless the task demands otherwise: their reasoning quality is tuned around default sampling, and cranking randomness mostly adds noise to the plan rather than brilliance to the answer.

  graded / structured work  -->  temperature=0
  creative work             -->  temperature=0.7-1.0
  5.x reasoning models      -->  defaults, unless you have a measured reason
You need byte-identical JSON from 1,000 runs. What do you set?

temperature=0. Deterministic output for graded, structured work.

Tool use: giving Claude hands

Rung 1: the plainest version. A model without tools can only talk. Tool use lets it act: query your database, call your APIs. The key insight the exam will probe: Claude never runs your tools. It only asks. Your code runs them and hands the results back.

  Claude: "I need order 48151623's status"   (a tool_use REQUEST)
     |
  Your code: runs get_order_status("48151623")   (the EXECUTION)
     |
  Claude: "Your order shipped Tuesday"   (final answer, with the data)

Rung 2: the loop. You describe tools as JSON Schema; Claude emits tool_use blocks when it needs data; you execute and return tool_result blocks with matching ids; you repeat until stop_reason is no longer tool_use. One turn can hold several tool_use blocks: run independent calls in parallel and return all results at once.

  your app                      Claude API
     |--- messages + tools -------->|
     |<-- tool_use blocks ----------|   stop_reason = "tool_use"
     |  (run functions here)
     |--- tool_result blocks ------>|   ids must match exactly
     |<-- tool_use blocks ----------|   (another round, if needed)
     |--- tool_result blocks ------>|
     |<-- final text ---------------|   stop_reason = "end_turn": done

# 1. DESCRIBE the tool. Claude decides when to call it from name + description.
#    Tool definitions ride along as input tokens on every call, so keep them tight.
tools = [
    {
        "name": "get_order_status",
        "description": "Look up a customer's order by numeric order id. Returns status and tracking number.",
        "input_schema": {  # JSON Schema: the contract for the arguments Claude may pass
            "type": "object",
            "properties": {
                "order_id": {"type": "string", "description": "Numeric order id, e.g. 48151623"}
            },
            "required": ["order_id"],
        },
    }
]

# 2. ASK. Claude either answers in text or emits tool_use blocks.
response = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    tools=tools,
    messages=[{"role": "user", "content": "Where is order 48151623?"}],
)

# 3. LOOP until Claude stops asking for tools.
MAX_TURNS = 20  # safety guard: a runaway loop bills you per turn
turns = 0
while response.stop_reason == "tool_use" and turns < MAX_TURNS:
    turns += 1
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            # 4. EXECUTE in your code. Claude only asked; you do the work.
            result = run_your_function(block.name, block.input)
            tool_results.append({
                "type": "tool_result",
                "tool_use_id": block.id,  # must match the request id exactly
                "content": result,
            })
    # 5. FEED BACK: assistant message (with tool_use) + user message (with results).
    response = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=1024,
        tools=tools,
        messages=response_messages_so_far + [
            {"role": "assistant", "content": response.content},
            {"role": "user", "content": tool_results},
        ],
    )
# stop_reason "end_turn": Claude is done. The final text is your answer.

Rung 3: the production picture. Two kinds of tools exist. Client tools run in your app: you define them, Claude requests them, you execute (everything above). Server tools run on Anthropic's side (web_search, web_fetch, code_execution, MCP connectors, tool_search): you declare them, Anthropic executes them, results arrive inside the response. tool_choice steers the behavior: auto (default), any (force at least one call), tool (force a specific tool), none (pure text this turn). And the billing reality: tool definitions count as input tokens on every call, so a 40-tool kitchen sink taxes every request.

  CLIENT tools:  you define -> Claude asks -> YOUR code runs -> you return results
  SERVER tools:  you declare -> Anthropic runs -> results arrive in the response

How to read this diagram: follow the green path first (user task becomes messages[], Claude thinks, stop_reason comes back tool_use). The orange diamond asks the only question that matters: tool call or final answer? YES goes right to your executor, which runs bash, read_file, write_file, or whatever tools you defined, then the orange dashed path carries tool_result back into messages[] and the loop repeats. NO drops down to the final response with stop_reason: "end_turn". The red dashed box is your billing seatbelt: MAX_TURNS = 20 stops a confused agent from looping forever.

How to read this diagram: steps 1 to 6 run in order, then step 6 asks "task done, or loop again?" The dotted arrow from step 5 back to step 2 is the whole game: every observation becomes new context for a better plan. The yellow box between choosing and executing is the permission gate (Allow / Ask / Deny): your rules decide what runs automatically, what needs approval, and what is blocked. The right-hand panel lists the available tools, and note that MCP servers and subagents expand the toolkit. The caption line at the bottom is worth memorizing: skills feed step 2, MCP expands step 3, hooks intercept step 4.

Decision: client tool or MCP server?

Build a client tool when the logic is yours: your database, your internal API, business rules only your code knows. The function lives in your codebase and you own its uptime.

Reach for an MCP server when the integration is standard: files, git, Postgres, Slack, web search. Someone already wrote and maintains that server; you configure it instead of coding it. One server, many hosts: the same MCP server plugs into Claude Code, your app, and your chat UI with zero recoding. (Full MCP unit coming up.)

The tool-use traps

Three classic failures. One: forgetting the loop. A single messages.create with tools only gets you the first tool request; without the loop you never see the answer. Two: mismatched tool_use_id. Every tool_result must carry the exact id of its tool_use block, or the API rejects the call. Three: no turn cap. An agent that keeps calling tools bills you every lap, so MAX_TURNS (or a cost budget) is mandatory.

Who executes a client tool: Claude or your code?

Your code. Claude only emits a tool_use request; your loop runs the function and returns the result as a tool_result block.

Thinking: letting Claude reason before it speaks

Rung 1: the plainest version. Some models think in a private scratchpad before answering. You see the final answer; the scratchpad stays hidden (or summarized) unless you ask for it.

  question --> [ thinking: private scratchpad ] --> answer

message = client.messages.create(
    model="claude-opus-5",
    max_tokens=16000,              # must leave room: thinking tokens + answer < max_tokens
    thinking={"type": "adaptive"}, # the model sizes its own reasoning effort
    messages=[{"role": "user", "content": "Design a retry strategy for this webhook flow..."}],
)
# The response interleaves thinking blocks (private) and text blocks (the answer).

Rung 2: adaptive thinking and the model map. On the 5.x generation, adaptive thinking means the model decides for itself how much reasoning a task needs, instead of you setting a token budget. As of September 2026: Opus 4.6 through 4.8 and Sonnet 4.6 support it (on 4.7 and 4.8 it is off by default, you must set it explicitly, and a manual budget_tokens there is rejected with a 400). Fable 5 and Mythos 5 have always-on adaptive thinking: no off switch. 5.x models also expose effort levels (low through xhigh) as a coarser dial.

  thinking={"type": "adaptive"}  -->  model judges the task, sizes its own effort
  effort="low" ... "xhigh"      -->  your coarse override, no token math
  thinking={"type":"adaptive"} on 4.7/4.8 without enabling  -->  off (must set explicitly)
  budget_tokens on 4.7/4.8      -->  400 error (rejected)

Rung 3: the production rules. Thinking blocks carry a signature you must pass back unmodified in later turns: it is an integrity seal, and tampering gets the call rejected. Thinking costs output tokens, so long reasoning on trivial tasks wastes money. And display: "summarized" gives users a readable summary of the reasoning instead of the raw scratchpad: use it in user-facing products.

  turn 1:  [thinking block + signature ABC] --> answer
  turn 2:  resend the thinking block with signature ABC UNCHANGED, or the API rejects the call
You pass thinking blocks back in a follow-up turn. What must you never change?

The signature. It must round-trip unmodified or the API rejects the request.

Prompt caching: pay for the prefix once

Rung 1: the plainest version. Every request reprocesses its input tokens. Prompt caching lets you pay full price to process a long, stable prefix once, then pay only 10% of the input price to reuse it for five minutes.

  call 1:  [ 20k system prompt ] + question  -->  pay FULL price (cache written)
  call 2:  [ 20k system prompt ] + question  -->  pay 10% for the prefix (cache hit)
  call 3:  [ 20k system prompt ] + question  -->  pay 10% for the prefix (cache hit)

message = client.messages.create(
    model="claude-sonnet-5",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": LONG_STABLE_PROMPT,  # 20k tokens of instructions, docs, examples
            "cache_control": {"type": "ephemeral", "ttl": "5m"},
            # ttl "5m" is the default. "1h" costs more to write, better for slow traffic.
        }
    ],
    messages=[{"role": "user", "content": user_question}],  # the changing part stays uncached
)

Rung 2: the prefix-match mechanic. A cache hit needs the request to start with exactly the cached bytes, in order. Anything above your cache_control checkpoint is cached; anything below it is processed fresh. Reorder the content or change one byte in the prefix and you get a miss. Design rule: stable content first (system prompt, tool definitions, reference docs), volatile content last (timestamps, user input). Never change tools or models mid-conversation: a new tool list is a new prefix.

How to read this diagram: the top box is your first request. Everything above the blue "Cache checkpoint" line (segments A, B, C) gets written to cache; D sits after the checkpoint and is processed fresh each time. The three boxes below are later requests. Left box starts with A, B, C in order: cache hit, you pay the 10% read price for the prefix. Middle box starts with B: the prefix differs, so cache miss, everything is processed at full price. Right box has the same content but reordered (E first): cache miss again, because matching is positional, not by content. Order is the contract.

Rung 3: the numbers and the verification habit. Max 4 breakpoints per request. Write price: 1.25x base input for 5-minute TTL, 2x for 1-hour TTL. Read price: 0.10x. Break-even: about 2 reads pay back a 5-minute write, about 3 reads pay back a 1-hour write. Minimum cacheable prefix: 512 tokens on the newest models, up to 4096 on some older ones. TTL is measured from the start of the request that wrote the cache. And the habit that separates production engineers from everyone else: check message.usage.cache_read_input_tokens on every call. If it stays near zero, your prefix is shifting and you are paying write prices for nothing.

  verify every call:  usage.cache_read_input_tokens >> 0  --> caching works
                      usage.cache_read_input_tokens ~= 0  --> prefix is shifting, fix the ordering
  break-even:  1 write at 1.25x is repaid by ~2 reads at 0.10x; reads after that are profit
Prompt caching numbers
  • Breakpoints: max 4 per request. A breakpoint is each cache_control marker.
  • Write price: 1.25x base input price for 5-minute TTL, 2x for 1-hour TTL.
  • Read price: 0.10x base input price. This is where the savings live.
  • Break-even: about 2 reads pay back a 5-minute write; about 3 reads pay back a 1-hour write.
  • Minimum cacheable prefix: 512 tokens on the newest models, up to 4096 on some older ones (Opus 4.6/4.5, Haiku 4.5 need 4096).
  • TTL is measured from the start of the request that wrote the cache.
Decision: should this request use prompt caching?

Cache when the same long prefix repeats across requests: system prompts, tool definitions, long reference documents, stable conversation history. Skip it when every request is genuinely new, when the prefix is under the minimum length, or when traffic is so sparse that the 5-minute TTL always expires between calls. Rough math: if a prefix will be read at least twice more within the TTL, caching wins.

A practitioner piece worth your time: 90% of Claude Apps Leak Context walks through the real-world failure mode, sending the whole conversation every turn and watching cache misses spike, with SDK patterns that fix it. The habit it teaches (cache the stable front, slice the history) is exactly what the exam rewards.

Your cache hit rate drops to zero after adding a timestamp to the system prompt. Why?

The timestamp changes the prefix on every request, so the prefix hash never matches and every call pays a fresh cache write.

The Batches API: half price, next day

Rung 1: the plainest version. Some workloads do not need an answer now: nightly evals, bulk classification, backfilling labels. The Batches API takes your requests, processes them within 24 hours, and charges 50% of standard prices.

  you:  [req 1] [req 2] ... [req 40,000]   --one batch-->
        ... up to 24 hours pass ...
  API:  [result 1] [result 2] ...           at HALF the normal price

Rung 2: the mechanics. One batch holds up to 100,000 requests or 256 MB. Each request carries your custom_id (1 to 64 characters, letters, digits, _, -), which comes back with its result so you can match them up. Poll processing_status: in_progress becomes ended. Each result is succeeded, errored, canceled, or expired.

batch = client.messages.batches.create(
    requests=[
        {
            "custom_id": "ticket-0001",  # your id: returned with the result for matching
            "params": {
                "model": "claude-haiku-4-5-20251001",
                "max_tokens": 512,
                "messages": [{"role": "user", "content": "Classify this ticket: ..."}],
            },
        },
        # ... up to 100,000 of these
    ]
)
# Poll batch.processing_status: in_progress -> ended.

  batch created  -->  processing_status: in_progress  -->  ended
       |                         |
  100,000 requests max     per-request: succeeded / errored / canceled / expired
  256 MB max                     matched to you by custom_id

Rung 3: the limits that matter. Results are kept for 29 days, then deleted: download them. Streaming is not supported in batches, and neither is max_tokens: 0. Cache behavior is best-effort. The exam loves this tradeoff question: when latency does not matter and volume is high, batches halve your bill.

  day 0: batch ended, results ready       day 29: results deleted (download first)
  supported: messages, tools, thinking    NOT supported: streaming, max_tokens: 0
You must label 40,000 support tickets by tomorrow morning. Batches or real-time calls?

Batches: 50% cheaper, 24-hour window fits, 40,000 requests is under the 100,000 limit.

Embeddings: the gap you must know about

Rung 1: the plainest version. Embeddings turn text into lists of numbers (vectors) so you can search by meaning instead of keywords. They power RAG retrieval, semantic search, and clustering.

  "refund policy"  -->  [0.21, -0.88, 0.44, ...]  -->  find nearby vectors = find related docs

Rung 2: the gap. Here is a fact that surprises people: Anthropic has no embeddings API. The Claude API returns text, not vectors. There is no endpoint that turns your documents into embeddings. The official docs point you to Voyage AI, Anthropic's recommended embeddings provider: you call Voyage for embeddings, store them in your vector database, retrieve the relevant chunks, and feed those chunks to Claude as context.

  your docs --> Voyage AI (embeddings) --> vector DB --> retrieve top chunks
                                                              |
  user question --> Claude API <-- retrieved chunks as context-+
  (Anthropic makes no vectors; the embedding box is third-party)

Rung 3: the exam trap. Any question asking which Anthropic endpoint returns embeddings has exactly one correct answer: none exists. Know the architecture above and you will never fall for it.

  exam stem: "Which Anthropic endpoint returns embeddings?"
  correct answer: none exists. Use a third-party provider such as Voyage AI.
Which Anthropic API endpoint returns text embeddings?

None. Anthropic offers no embeddings API; the documented path is a third-party provider such as Voyage AI.

The model lineup: practitioner level

Rung 1: the plainest version. Four tiers, cheapest to dearest. Price tracks intelligence, and you do not need benchmark scores for the exam, only the selection logic.

  Haiku 4.5  <  Sonnet 5  <  Opus 5.5  <  Fable 5.1
  $1 / $5        $2 / $10       $4 / $20       $10 / $50   (per MTok in/out)
  fast+cheap     workhorse       hard jobs       hardest reasoning
Model API family id Context Max output Input / output per MTok Reach for it when
Fable 5.1 claude-fable-5-1 1M tokens 128K $10 / $50 Hardest reasoning; always-on adaptive thinking
Opus 5.5 claude-opus-5 1M tokens 128K $4 / $20 Complex agents, high-stakes decisions

Rung 2: routing by task. The production pattern is tiering, not prestige: Haiku handles extraction and formatting, Sonnet handles reasoning steps, Opus or Fable handles the few decisions where being wrong is expensive. A model that 429s at step 4 of a 12-step pipeline is not a genius, it is a bottleneck.

  incoming work --> router (by task complexity + cost of being wrong)
       |-- trivial: extract, format, classify --> Haiku 4.5
       |-- standard: reason, draft, decide     --> Sonnet 5
       |-- critical: high-stakes judgment      --> Opus 5.5 / Fable 5.1

Rung 3: ids, windows, and compounding math. Family ids (claude-sonnet-5) track the latest snapshot automatically; dated ids (claude-haiku-4-5-20251001) pin one exact snapshot. Pin for reproducibility (evals), track for freshness (production chat). A 1M context window means you can send a million tokens, not that you should: cache-creation cost and latency scale with what you actually send. Effort levels (low through xhigh) on 5.x models give coarse control over reasoning depth. And the price math compounds: batches cost 50% of list, cache reads cost 10% of input price, so a Haiku batch call with a warm cache is roughly twenty times cheaper than a cold Fable call.

  cost per 1M Haiku input tokens:
    standard $1.00  -->  batch (50%): $0.50  -->  warm cache read (10%): $0.05
  ids:  claude-sonnet-5            family id: tracks the latest snapshot
        claude-haiku-4-5-20251001  dated id: pins one exact snapshot
Your pipeline classifies 2M tickets a month and summarizes 50 escalations. Which models?

Haiku for the bulk classification (cheap, fast), Sonnet or Opus for the 50 escalations where quality matters.

MCP: the universal connector

Rung 1: the plainest version. Without a standard, every app rebuilds the same integrations: N apps times M tools, every pair hand-built. The Model Context Protocol turns N x M into N + M: each app speaks MCP once, each tool speaks MCP once, and any pair connects.

  WITHOUT:  app1-tool1  app1-tool2  app2-tool1  app2-tool2 ...  (N x M hand-built pairs)

  WITH:     app1 --\
  MCP         app2 ----> MCP  <---- tool1
  standard    app3 --/   standard    tool2          (N + M: each side implements once)

Rung 2: the three roles and three primitives. MCP is an open standard Anthropic published in November 2024, running on JSON-RPC 2.0. The host is the app the user touches (Claude Code, your chat UI): it owns the conversation and the permissions. The client lives inside the host, one per server, speaking the protocol on the host's behalf. The server exposes capabilities to the outside world. A server offers three primitives: tools (things the model can do), resources (data the model can read), prompts (reusable instruction templates).

How to read this diagram: the big rounded box is the host (your app). Inside it sit two MCP clients, one per integration. Each client talks through the MCP protocol to its own MCP server on the right. Add a third integration and you add one client plus one server: no changes to the existing pairs. That is the N + M payoff, drawn.

  HOST (your app)                    PROTOCOL        SERVERS
  +---------------+                                       +----------+
  | MCP client #1 | ---- MCP (JSON-RPC 2.0) ------------> | Postgres |  tools/resources/prompts
  | MCP client #2 | ---- MCP (JSON-RPC 2.0) ------------> | Slack    |  tools/resources/prompts
  +---------------+                                       +----------+
  add a server = add one client. Existing pairs untouched.

Rung 3: MCP inside the Claude API. In the API, MCP appears as server tools (MCP connectors): you declare the connector, Anthropic runs it on its infra, results arrive inside the response. Compare with the tool-use unit: client tools run your code, MCP connectors run Anthropic's infra against a standard server. Build a client tool when the logic is yours (your database, your business rules); reach for an MCP server when the integration is standard (files, git, Postgres, Slack) and someone already maintains it.

What problem does MCP solve, in one sentence?

The N x M integration problem: without it every app hand-builds every tool integration; with it each app and each tool implements the standard once.

Claude Code and the Agent SDK: user level

Rung 1: the plainest version. Two ways to get agents without hand-rolling the tool loop yourself. Claude Code is Anthropic's terminal agent: it edits code, runs shell commands, and reads your repo on its own. The Agent SDK is the toolkit for building your own agents in Python or TypeScript, using the same loop primitives.

  Claude Code:  terminal --> agent works on YOUR codebase (you use it)
  Agent SDK:    your code --> agent lives inside YOUR product (you build it)

Rung 2: the safety model and the selection rule. Claude Code runs every action through a permission gate: Allow (routine reads run free), Ask (destructive commands need approval), Deny (blocked outright). Your rules decide what lands where. The selection rule is simple: if the job is "work on this codebase," open Claude Code; if the job is "embed an agent inside my product," build on the Agent SDK.

  agent wants to act --> permission gate --> ALLOW (read file) / ASK (delete db) / DENY (exfiltrate)

Rung 3: what is underneath. Both sit on the same Messages API mechanics you already learned: stateless turns, tool_use loops, and prompt caching doing the heavy cost lifting underneath. Nothing here is magic; it is the earlier units, packaged.

  Claude Code / Agent SDK  (packaging)
        |
  Messages API: stateless turns + tool_use loop + prompt caching  (mechanics)
Your product needs a support agent inside your own UI. Claude Code or Agent SDK?

Agent SDK. Claude Code is a terminal tool for working on code; the SDK builds agents you embed in your product.

Streaming: tokens as they arrive

Rung 1: the plainest version. By default the API waits until the full response is ready. Streaming flips that: tokens arrive as server-sent events (SSE) while Claude is still generating, so your UI renders text word by word like a chat app.

  non-streaming:  wait .................... --> full answer at once
  streaming:      "The" " quick" " brown" ... --> words appear as generated

Rung 2: the event sequence. Each token chunk arrives as a content_block_delta; the SDK reassembles them, and get_final_message() returns the same message object a non-streaming call would. Thinking blocks stream as thinking_delta and signature_delta.

# The SDK reassembles the events for you. get_final_message()
# returns the same message object a non-streaming call would.
with client.messages.stream(
    model="claude-sonnet-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Write a haiku about caching."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)  # render each chunk live
    final = stream.get_final_message()   # usage, stop_reason, full content

  message_start
    -> content_block_start -> content_block_delta (x many) -> content_block_stop
    -> message_delta
    -> message_stop

Rung 3: when to stream, and the failure mode. Stream when a human is watching (chat UI, long generations where perceived latency matters). Do not stream when no one is watching: batch jobs, tool-use loops that only need the final object, evals. And if something fails mid-stream, it arrives as an error event, not an HTTP error code, so your handler must watch for it. Streaming changes delivery, not cost or quality.

  human watching? --yes--> stream (chat UI, long generations)
       |
       no --> don't stream (batches, tool loops, evals)
  mid-stream failure arrives as an "error" EVENT, not an HTTP code
Your nightly eval runs 5,000 prompts through the Batches API. Stream or not?

Not. Nobody watches a batch job, and batches do not support streaming anyway.

Rate limits: RPM, ITPM, OTPM

Rung 1: the plainest version. Anthropic throttles usage on three dials: RPM (requests per minute), ITPM (input tokens per minute), OTPM (output tokens per minute). Limits rise with your usage tier.

  your app --> [ RPM | ITPM | OTPM ] --> Claude API
                  ^^^^^^^^^^^^^^^^^
                  three dials, all must stay under the cap

Rung 2: the 429 dance. Hitting a limit returns 429 with a retry-after header telling you how long to wait. The production pattern is boring and mandatory: catch 429, wait the advertised time, retry with backoff. Do not hammer the endpoint; the limit will not move because you asked twice.

  call --> 429 (retry-after: 12s) --> wait 12s --> retry --> 200
                                      (backoff grows if it 429s again)

Rung 3: two 429s that mean different things. A rate-limit 429 carries retry-after: wait and retry, automatically. A tier-cap 429 comes without retry-after: you hit a spend cap, not a speed limit, and retrying is pointless. Raise the cap or wait for the reset. Related: if your own spend limit trips, the API answers 400 (invalid_request_error), not 429. A 400 that appears only after weeks of working code is usually money, not syntax.

  got 429:
    has retry-after? --yes--> rate limit: wait, back off, retry automatically
    has retry-after? --no----> tier spend cap: STOP retrying, raise cap or wait
  got 400 on old working code --> likely your spend limit tripped, check billing
You get a 429 with no retry-after header. What happened and what do you do?

You hit a tier spend cap, not a rate limit. Stop retrying; raise the cap or wait for the reset.

Errors and retries: the codes that matter

Rung 1: the plainest version. Error codes split two ways: 4xx means your fault (fix the request), 5xx means their fault (retry with backoff). The SDK already retries transient failures (429, 500, 529) twice, with exponential backoff that honors retry-after.

  4xx (400,401,403,404,413)  -->  YOUR bug: fix the request, do not just retry
  5xx (500,504,529) + 429    -->  THEIR problem: back off and retry

Rung 2: the codes that matter.

Code Meaning Your move
400 Bad request (bad params, spend limit tripped) Fix the request; check spend caps if code used to work
401 Bad API key Rotate the key, check the environment variable
402 Billing issue Add credits / fix payment method
403 Forbidden Key lacks access to that model or feature
404 Not found Wrong model id or endpoint
409 Conflict Retry the idempotent operation
413 Payload too large Request exceeds 32 MB; shrink context or attachments
429 Rate limited Honor retry-after, back off
500 Anthropic side error Retry with backoff
504 Gateway timeout Retry; consider smaller requests
529 Overloaded Retry with backoff; the service is saturated

Rung 3: your responsibilities around the retry. Retries are safe only when repeating the call is harmless, so tool functions must be idempotent: a retried charge must not double-bill a customer. Build a dead-letter path for requests that fail after retries, and alert on 4xx spikes, which are your bug, not Anthropic's. Size limits to keep in your head: 32 MB per Messages request, 256 MB per batch, 500 MB for file uploads. Past those, the answer is 413 and the fix is chunking.

  retry safe?  tool is idempotent --yes--> retry freely (charge(42) twice = charged once)
                                    no   --> make it idempotent first, or don't auto-retry
Your tool charges a customer per call. A request times out and the SDK retries. What breaks?

A double charge, unless the tool function is idempotent. Retries are safe only when repeating the call is harmless.

Eval basics: measure, then trust

Rung 1: the plainest version. Prompt engineering makes a prompt better. Evaluation tells you whether it is good enough, with a number instead of a feeling. Test the prompt the way you test code: run it against known cases and score it.

  prompt + test cases --> run --> score (e.g. 82% correct)
  change the prompt  --> run --> score (e.g. 91% correct)  --> the delta is the truth

Rung 2: the four-step loop. Draft the prompt. Build data: inputs with known-good outputs (50 to a few hundred examples beats vibes). Run the prompt over the dataset. Score with a deterministic check first (exact match, JSON parses, regex), and only then with a model grader for the fuzzy parts. Then change the prompt and run the loop again. Manual spot-checking lies to you: you remember the wins and forget the failures.

  1. DRAFT prompt
  2. BUILD dataset (inputs + known-good outputs)
  3. RUN over the dataset (Batches API: half price, no hurry)
  4. SCORE: deterministic checks first, model grader second
        |
        v  (loop: edit prompt, re-run, compare the delta)

Rung 3: the production setup. The Batches API is the eval workhorse: 50% off, and evals never needed low latency. The exam-ready distinction: prompt engineering edits the instruction; evaluation measures the behavior across many inputs. Teams that skip the second one ship prompts that work on the five examples the author tried and fail on the five thousandth user.

Safety and guardrails: the short version

Rung 1: the plainest version. Claude is trained with a safety-first approach (Anthropic calls it constitutional AI), aimed at making it helpful, honest, and harmless, and the API refuses certain content outright. But model-level safety is only one layer. The exam treats safety as an architecture concern, not a model feature.

  safety = layers, not a model feature
  [ input checks ] -> [ model ] -> [ output checks ] -> [ human review ]

Rung 2: the four layers. Input validation strips what your app should never forward: prompt-injection attempts pasted into user fields, absurd payloads, malformed tool arguments. The model gets system prompts stating refusal and escalation rules, and the right model for the risk level. Output checks validate structure (does it parse as JSON?), scan for disallowed content, and route high-stakes outputs (refunds, medical, legal) to human review before they reach the user. Audit trail logs prompts, tool calls, and outputs so you can replay exactly what happened.

  user input --> [1. validate: injections, size, shape]
             --> [2. model: refusal rules in system prompt]
             --> [3. check output: parse, scan, escalate if high-stakes]
             --> [4. log everything: replayable audit trail]
             --> user

Rung 3: the mindset. Never trust a single layer. The model is one guardrail among several, and your architecture owns the rest.

  one layer fails --> breach.  layered: one fails, the next catches it.
  [input] [model] [output] [human] [audit]: remove any ONE, still defended
Name two safety layers that live outside the model.

Any two of: input validation, output checks, human review for high-stakes outputs, audit logging.

Prompt engineering fundamentals: the five moves

Rung 1: the plainest version. Everything about writing better prompts starts with one move: be explicit. "Summarize this" is a wish; "three bullets, under 40 words, for a busy exec" is an instruction. Wishes get whatever the model feels like; instructions get what you asked for.

  wish:        "Summarize this"                                    --> unpredictable
  instruction: "Three bullets, under 40 words, for a busy exec"    --> what you asked for

Rung 2: show and structure. Move two: show examples. Two or three input-output pairs (few-shot) teach format and tone faster than paragraphs of description. Move three: structure with XML tags. Wrap sections in <context>, <instructions>, <examples> so Claude gets parseable landmarks, especially in long prompts.

  <context> the background Claude needs </context>
  <instructions> exactly what to do </instructions>
  <examples> 2-3 input/output pairs showing the format </examples>

Rung 3: reason, then measure. Move four: ask for reasoning on hard tasks. Tell it to think step by step, or enable thinking mode; reasoning quality drives answer quality. Move five: iterate with evals. Every edit gets measured on the dataset, or it did not happen. The failure mode is prompt superstition: phrases people add because they heard it helps, with no measurement. If an edit does not move your eval score, delete it. Shorter prompts are cheaper, faster, and easier to cache.

  edit prompt --> run eval --> score moved? --yes--> keep it
                                            no   --> delete it (superstition)
A teammate adds three paragraphs of motivational fluff to the system prompt. Eval score unchanged. Keep it?

No. Unmeasured prompt weight costs tokens every call and breaks nothing by leaving. Delete it.

How to read this diagram
  1. Request arrives. The chat UI opens a streaming call so the customer sees words immediately.
  2. The app assembles the request. Cached system prompt first (stable prefix), then the conversation history, then the new message. Tool definitions ride along as input tokens.
  3. Routing picks the model. Haiku triages the ticket in one cheap call. Routine questions stay on Sonnet. Anything involving money or angry enterprise accounts escalates to Opus 5.5 with adaptive thinking.
  4. The tool loop runs. Claude asks for get_order_status; your code runs it and returns the tool_result with the matching id. The CRM lookup goes through the MCP connector instead: no custom code, just configuration. The loop repeats until stop_reason is end_turn, capped at 20 turns.
  5. The answer streams back. Thinking summaries show for escalations; raw scratchpad never reaches the user.
  6. Failures are handled, not hoped away. Rate-limit 429s back off automatically. Tier-cap 429s alert a human. Tool functions are idempotent so retries never double-charge. Every turn logs token usage and cache hits.
  7. Nightly, the batch eval runs. Five hundred labeled tickets go through the Batches API at half price. If the score drops, the prompt change that caused it gets reverted. Nothing ships on vibes.
  8. Guardrails wrap everything. Injection attempts die at input validation. Refund decisions queue for human review. The full audit trail replays any incident end to end.
