F1 Architecture and business foundations

Token cost model

Each token class has its own price, so the cost of a request is the sum of its classes.

Schematic drawn from docs. Arrows: 1. send request. 2. return token counts. 3. count per class. 4. rate per class. 5. times daily volume.
  • The API reports token counts for each class in the usage fields.
  • Cache writes and cache reads have their own multiplier on the base input price.
  • Thinking tokens bill as output tokens.
  • Batch requests cost 50 percent less than standard requests.
  • Claude Sonnet 5.5 costs 2 dollars per million input tokens and 10 dollars per million output tokens.1
  • Claude Opus 5.5 costs 4 dollars per million input tokens and 20 dollars per million output tokens.1
  • Claude Haiku 5.5 starts at 0.10 dollars per million input tokens and 0.50 dollars per million output tokens.2
  • Multiply each token class by its own rate, add the classes, then multiply by the request volume.

F1. Expect a scenario with a price, a volume, and a request for a monthly figure. The credited answer uses token arithmetic per class. (Inference)

A flat estimate that counts input tokens only looks simple, but output tokens cost more, so the estimate understates the bill.

F2 LLM foundations

Context window

The context window holds every input token and every output token of a turn, so all of them share one budget.

Schematic drawn from docs. Arrows: 1. counts toward window. 2. counts toward window. 3. generate turn. 4. caps output. 5. ends with reason.
  • Everything in a request counts toward the context window.
  • The system prompt, the messages, the tool results, and the tool definitions all count.
  • Thinking tokens and text output count too.
  • The max_tokens value caps the output for each response.
  • Claude Opus 5.5 has a 1M-token context window.1
  • Models with a 1M-token context window generate up to 128k output tokens in one request.5
  • Other models, such as Claude Sonnet 4.5, have a 200k-token context window.5
  • Fit the request inside the window with room for max_tokens, then select what enters the window.

F2. Expect a long document and an output limit in one scenario. The credited answer checks the window and max_tokens before the design. (Inference)

A bigger window looks like the fix for missed details, but context rot means more tokens can lower recall.

F3 Software and distributed systems

Error classes and retry

Each error type tells the caller whether a retry can help.

Schematic drawn from docs. Arrows: 1. send request. 2. return status and type. 3. 429, 500, or 529. 4. 400 or 401. 5. resend after delay. 6. record request-id.
  • The API returns an HTTP status code and an error type for each failure.
  • A 400 invalid_request_error means the request needs a fix, so a retry does not help.
  • A 401 authentication_error means the key needs a fix, so a retry does not help.
  • A 429 rate_limit_error can succeed after a wait.
  • The official SDK retries connection errors, rate limits, and 5xx errors twice by default.7
  • When a rate limit response has a retry-after header, wait that many seconds before retrying.3
  • A 500 api_error means an unexpected internal error, and the docs say to retry with exponential backoff.7
  • Retry 429 and 5xx errors with a limit and backoff. Fix 400 and 401 errors first.

F3. Expect a stem that shows a call that fails. The credited answer matches the error class to a fix in the caller. (Inference)

A prompt that says try again looks like a retry policy, but the model cannot resend the request or read a retry-after header.

Timeouts and long requests

A request that runs too long can lose its connection, so long work uses a stream or a batch.

Schematic drawn from docs. Arrows: 1. read events. 2. idle drops risk. 3. create batch. 4. check status. 5. download when ended.
  • Use streaming for a long response, so your app reads events as they arrive.
  • The SDK checks that a Messages request that does not stream is not expected to pass a 10-minute timeout.
  • Set a TCP keep-alive on direct integrations to reduce idle drops.
  • Create a Message Batch for work that the user does not wait for.
  • The SDK validates that Messages requests that do not stream are not expected to exceed a 10-minute timeout.7
  • Some networks drop idle connections after a variable period.7
  • Most batches complete within 1 hour.8
  • Stream when the user waits, and batch when the caller can poll later.

F3. Expect a long job and a user who either waits or does not wait. The credited answer picks streaming or a batch by who waits. (Inference)

A longer client timeout looks like the fix for long calls, but idle connections can drop on some networks no matter the timeout.

Streaming events and errors

A stream sends typed events after a 200 status, so an error can arrive inside the stream.

Schematic drawn from docs. Arrows: 1. request stream. 2. send events. 3. apply delta events. 4. overloaded_error event. 5. assemble message.
  • The API sends server-sent events after a 200 status.
  • Ping events can appear at any point in the stream.
  • Delta events add partial content to a content block.
  • An error event can arrive in the stream, for example an overloaded_error.
  • An error can occur after the API returns a 200 response during a server-sent event stream.7
  • An overloaded_error in a stream would normally correspond to HTTP 529.9
  • Event streams can include any number of ping events.9
  • Handle error events inside the stream loop. Do not rely on the HTTP status check alone.
