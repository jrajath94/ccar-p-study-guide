How to use this bank

Read the scenario, then read the constraint box. The constraint is the scoring key: several options will be partly right, and the credited answer is the one that best satisfies the stated constraint (accuracy SLA, latency budget, compliance rule, cost ceiling). Find the numbers and rules in the scenario first, then judge each option against them. An option that is good engineering but breaks the constraint is a distractor. Pick your answer before opening the explanation panel. Each explanation gives the correct answer, why it wins, and why every other option loses.

Key terms used in this bank

Every term below appears in at least one question. Each is defined once, here, before its first use. Read this section once, then the questions can assume the vocabulary.

Retrieval and RAG

TermMeaning
RAG (Retrieval-Augmented Generation)Answering from your own documents: the system retrieves relevant passages and the model answers from them, instead of answering from memory.
ChunkOne small retrievable piece of a document. Chunking is the decision of where to cut.
EmbeddingA long list of numbers that captures the meaning of a piece of text. Similar meanings land near each other.
VectorThe embedding stored as a point in a mathematical space, so the database can find "nearby" meanings fast.
MetadataFacts stored alongside a chunk, such as document ID, section, or date, used to filter before the similarity search.
Top-kThe k highest-scoring chunks returned by retrieval, for example the top 5.
RerankA second, slower model that re-scores the retrieved chunks and keeps only the best few. Cheap recall first, careful precision second.
Semantic searchSearching by meaning (embeddings), so "car" matches "automobile".
Keyword searchSearching by exact words (such as BM25, a classic word-frequency ranking formula), so "car" does not match "automobile".
Hybrid searchRunning semantic and keyword search together and merging the results, to catch both meaning and exact terms.
PrecisionOf the chunks retrieved, how many were actually relevant.
RecallOf all the relevant chunks that exist, how many the retrieval found.
FaithfulnessThe share of the answer's claims that are verifiable against the retrieved text. The opposite of hallucination.
HallucinationThe model stating something as fact that is not supported by its sources.
ROUGEA score that measures word overlap between a generated summary and a reference summary. It rewards similar wording, not truthfulness.

Models and context

TermMeaning
TemperatureA setting that controls randomness: low temperature makes the model pick the most likely token each time, high temperature makes it sample more freely.
Context windowThe maximum amount of text (prompt plus history plus retrieved chunks) the model can consider in one request.
Zero-shotAsking the model to do a task with instructions only, no examples.
Few-shotShowing the model a few worked examples inside the prompt before asking it to do the task.
Chain-of-thoughtAsking the model to reason step by step before giving the final answer, which usually improves accuracy on hard problems.
Prompt cachingPaying full price once for the stable part of a prompt, then a tenth of the price when the same prefix is reused within a few minutes.
LLM judgeUsing a language model, guided by a scoring rubric, to grade another model's outputs at a scale humans cannot match.
Golden setA frozen, versioned collection of test cases with known-good answers that every change is scored against.

Integration and reliability

TermMeaning
MCP (Model Context Protocol)The open standard that connects Claude to external tools and data through small services called MCP servers.
OAuth 2.0The industry standard for delegated sign-in: the user logs in once and the service receives a narrowly scoped token instead of a shared password or API key.
SSO (single sign-on)One login that grants access to many company systems, managed centrally by IT.
SandboxAn isolated execution environment where untrusted code or tools can run without touching real systems.
TimeoutA maximum wait: if the tool or model call takes longer, it is cut off and treated as failed.
RetryCalling again after a failure. Safe only for idempotent operations (ones where running twice has the same effect as running once).
Circuit breakerA guard that stops calling a failing service for a while, so retries do not pile onto an outage.
BulkheadA cap on how many calls can hit one dependency at once, so one slow partner cannot consume every worker.
Rate limitA cap on how many requests a caller may make in a time window.
CanaryReleasing a change to a small slice of traffic first and watching the metrics before rolling it out fully.
RollbackReverting to the previous working version when a release misbehaves.

Measurement

TermMeaning
SLA (service-level agreement)A promised target, such as "95 percent accuracy" or "answer within 2 seconds", that the design must meet.
p95 latencyThe latency that 95 percent of requests beat. If p95 is 2 seconds, 5 percent of users wait longer.
LatencyHow long one request takes, end to end.
ThroughputHow many requests the system handles per unit of time.
A/B testRouting part of the traffic to version A and part to version B, then comparing measured outcomes to decide which ships.

Governance and safety

TermMeaning
PII (personally identifiable information)Data that identifies a person: names, emails, phone numbers, addresses, account numbers.
PHI (protected health information)Health data covered by HIPAA: diagnoses, visit notes, prescriptions, anything tying health facts to a patient.
GDPRThe European privacy regulation: it governs how personal data of EU residents may be collected, stored, and processed.
HIPAAThe US health-privacy law. Processing PHI requires a signed BAA with the vendor.
FedRAMPThe US federal program that authorizes cloud services to handle government data, with graded impact levels.
BAA (Business Associate Agreement)The contract a vendor signs promising to safeguard PHI. Only certain plans and surfaces are BAA-eligible.
ZDR (zero data retention)A contractual promise that the provider stores none of your request or response data after serving it.
Data retentionHow long a provider keeps your prompts and outputs, and under what terms.
Human-in-the-loop (HITL)A design where the system pauses and a person approves before a sensitive or irreversible action proceeds.
Red teamA group that attacks the system on purpose (jailbreak attempts, injection, misuse) to find weaknesses before real attackers do.
JailbreakA prompt crafted to make the model bypass its own safety rules.

Easy items

Q1D3EasySelect one
A legal-tech startup builds a contract question-answering assistant over 40,000 vendor contracts. Users ask questions like "What is the termination notice period in contract ACME-2024-118?" and expect the exact clause quoted. The team is designing the RAG pipeline and must choose a chunking strategy.
Constraint: answers must cite the exact clause. Small errors in clause text are unacceptable to the legal team.
Which chunking strategy best satisfies the constraint?
  1. Split each contract into 2,000-token chunks with no overlap, to keep each clause in rich surrounding context.
  2. Split each contract into 400 to 600-token chunks with 10 percent overlap, and attach contract ID plus section heading as metadata on every chunk.
  3. Embed each full contract as a single vector and retrieve the whole contract, letting the model find the clause.
  4. Chunk by fixed 100-token windows with no overlap or metadata, to maximize retrieval precision.
Show answer and explanation
Answer: B

Why B is correct: the constraint is exact clause citation. Small chunks raise retrieval precision so the cited clause is actually returned, overlap prevents clauses split across boundaries from being lost, and metadata (contract ID, section) lets the system filter and cite correctly.

  1. A is wrong because 2,000-token chunks dilute precision: the retriever returns long passages and the model may quote the wrong clause from the same chunk.
  2. C is wrong because a whole contract far exceeds useful retrieval granularity; the model cannot reliably locate one clause in 40,000 embedded documents.
  3. D is wrong because 100-token windows with no overlap will slice clauses in half, and without metadata the system cannot attribute a quote to the right contract.
Q2D3EasySelect one
A sales team wants a Claude agent that can look up accounts and update opportunities in their CRM. The CRM exposes a stable, well-documented REST API with six endpoints. One engineer proposes building an MCP (Model Context Protocol) server; another proposes calling the REST API directly through function calling.
Constraint: ship in two weeks with the smallest maintenance surface. Only this one CRM is in scope.
Which integration approach should the architect choose?
  1. Build an MCP server, because MCP is the standard and will be required for future tools.
  2. Call the CRM REST API directly through function calling, since there is one stable API and six endpoints.
  3. Build both an MCP server and direct REST tools, so the agent can choose at runtime.
  4. Use an agent-to-agent protocol so the CRM can negotiate with the Claude agent directly.
Show answer and explanation
Answer: B

Why B is correct: MCP pays off when there are many tools, dynamic discovery, or shared servers across agents. With one stable API and a two-week deadline, direct function calling is simpler and has less to maintain, which is exactly what the constraint asks for.

  1. A is wrong because "MCP is the standard" is not a reason by itself; it adds a server to build, host, and secure for no capability gain here.
  2. C is wrong because maintaining two integration paths doubles the maintenance surface, the opposite of the constraint.
  3. D is wrong because agent-to-agent protocols connect agents to agents, not agents to a REST API; the CRM is not an agent.
Q3D3EasySelect one
A support agent was given 47 tools: every internal API got its own function. After launch, the team sees slow responses and frequent wrong-tool calls. The model often picks a roughly similar tool instead of the right one, then retries.
Constraint: reduce wrong-tool calls without removing any capability the agent needs.
What is the best fix?
  1. Upgrade to a larger model so it can handle 47 tools more reliably.
  2. Add five more helper tools that pre-select the right tool for common cases.
  3. Group tools into fewer, well-named functions (or namespaced MCP servers) so the agent sees a small set of distinct choices, with details revealed on demand.
  4. Raise the temperature so the agent explores different tools more creatively.
Show answer and explanation
Answer: C

Why C is correct: this is tool bloat. A flat list of 47 similar tools makes selection a guessing game. Grouping into a small set of distinct, well-named entry points (progressive disclosure of the rest) cuts wrong-tool calls while keeping every capability reachable.

  1. A is wrong because a larger model costs more and adds latency, and it treats the symptom (bad selection) instead of the cause (47 indistinguishable options).
  2. B is wrong because adding tools makes the bloat worse, not better.
  3. D is wrong because higher temperature increases randomness, which increases wrong-tool calls.
Q4D3EasySelect one
An internal Claude agent reads and files expense reports through the finance API. It authenticates with a single shared service token that has full read and write access to every employee's expenses. A security review flags this before launch.
Constraint: the agent must act only within the requesting employee's own permissions. No shared privileged credential.
Which auth design resolves the finding?
  1. Keep the shared token but rotate it weekly.
  2. Give the agent one token per employee, all with full admin scope, stored in the agent's config file.
  3. Use OAuth 2.0 delegated tokens: each request carries the requesting user's own token, scoped to least privilege.
  4. Remove authentication entirely and rely on the office VPN for access control.
Show answer and explanation
Answer: C

Why C is correct: OAuth delegated (user) tokens make the agent act as the user with only that user's permissions. This satisfies least privilege and removes the shared privileged credential entirely.

  1. A is wrong because rotation does not change the blast radius: one leaked token still reaches everyone's expenses.
  2. B is wrong because per-employee admin tokens are still over-privileged, and storing them in a config file creates a new secret-sprawl problem.
  3. D is wrong because the VPN proves network location, not user identity or authorization; any user on the VPN could reach anyone's expenses.
Q82D3EasySelect one
An e-commerce agent answers "is this in stock?" A proposal would index the inventory database into the vector store, refreshed hourly, so the agent can answer from retrieval.
Constraint: the agent must never promise stock that is not actually there; an oversell means a refund and an angry customer.
Where should live inventory levels come from?
  1. The hourly vector index, since retrieval is fast.
  2. A direct tool call to the inventory system at decision time; the vector index holds stable knowledge, not mutable state.
  3. A twice-hourly vector index, which is fresher.
  4. The model's training knowledge of typical stock levels.
Show answer and explanation
Answer: B

Why B is correct: inventory is live state: it changes between any two index refreshes. Only a read at decision time reflects reality; a vector index is for stable knowledge, and even a 30-minute-old snapshot can oversell.

  1. A is wrong because an hourly snapshot is stale by definition; anything sold in the last hour is invisible to it.
  2. C is wrong because refreshing twice as often halves the staleness window but keeps the structural flaw, at double the indexing cost.
  3. D is wrong because training knowledge is months old and was never about this store's stock.

Q5D3MediumSelect one
A chat triage agent classifies incoming support tickets. The current design uses a large model with long chain-of-thought reasoning: accuracy is 93 percent, but p95 latency is 6 seconds. The product requirement is p95 latency under 2 seconds with accuracy at or above 90 percent. Ticket volume is 300,000 per month.
Constraint: p95 under 2 seconds AND accuracy at or above 90 percent. Both must hold at 300K tickets per month.
Which design best meets both bars?
  1. Switch everything to the smallest, fastest model and accept whatever accuracy results.
  2. Keep the large model but cut the output token limit in half to reduce latency.
  3. Route with a fast model first; escalate to the large model only when the fast model's confidence is low. Verify the mix on a labeled eval set.
  4. Cache every ticket classification so repeat tickets never hit the model.
Show answer and explanation
Answer: C

Why C is correct: tiered routing (fast model first, escalate on low confidence) gets most tickets under the latency bar while the large model protects the accuracy bar on hard cases. The eval-set check proves both bars hold before launch, which is what the constraint demands.

  1. A is wrong because it guarantees the latency bar but abandons the accuracy bar; "accept whatever accuracy" violates the stated 90 percent floor.
  2. B is wrong because cutting output tokens does not reliably cut 6 seconds to under 2, and it risks truncating the reasoning the 93 percent accuracy depends on.
  3. D is wrong because support tickets are mostly unique; cache hit rates will be near zero, so this changes almost nothing.
Q6D3MediumSelect one
A production assistant handles 2 million requests per day across search, summarization, and tool calls. The team wants to detect quality drift, especially hallucinations, within one day of it starting. Today they only log the final user-facing text.
Constraint: detect hallucination drift within 24 hours at 2M requests per day, without storing every full prompt and completion (too expensive).
Which observability strategy fits?
  1. Log only error responses and review them weekly.
  2. Store every prompt and completion in full, and hire reviewers to read them.
  3. Emit structured traces (one span per tool call and model call with token counts and latency), sample a fraction of full transcripts, and run an automated faithfulness eval over the sample daily.
  4. Track only aggregate latency and token cost dashboards.
Show answer and explanation
Answer: C

Why C is correct: structured traces give cheap always-on coverage of behavior, sampling keeps storage affordable at 2M requests per day, and a daily automated faithfulness eval on the sample detects hallucination drift inside the 24-hour window.

  1. A is wrong because hallucinations rarely raise errors; error logs miss them entirely, and weekly review misses the 24-hour window.
  2. B is wrong because full logging at 2M requests per day violates the cost constraint, and manual review cannot keep up.
  3. D is wrong because latency and cost dashboards say nothing about answer quality; drift would be invisible.
Q7D3MediumSelect two
An IT helpdesk agent handles two query patterns: (1) "find the three most similar past incidents to this error message" (fuzzy, wording varies), and (2) "what is the status of incident INC-48210" (exact lookup by ID). The team is choosing a retrieval strategy over the incident database.
Constraint: both query patterns must return correct results. Fuzzy queries need semantic matching; exact queries must never return a "similar but wrong" incident.
Which two approaches together satisfy the constraint? (Select two.)
  1. Use dense vector (semantic) search for the fuzzy similar-incident queries.
  2. Use exact keyword matching on the full error text for the fuzzy similar-incident queries, so results stay deterministic.
  3. Use dense vector search for both patterns, trusting the embedding to rank INC-48210 first.
  4. Route the query first: detect an incident ID pattern and send it to exact lookup, otherwise use semantic search.
Show answer and explanation
Answer: A, D

Why A, D is correct: the constraint has two halves. A supplies the right mechanism for the fuzzy half (dense semantic search). D supplies the routing rule: detect an incident ID and send it to exact lookup, otherwise use semantic search. Together they cover both query patterns with the right mechanism each time.

  1. B is wrong because exact keyword matching cannot handle the fuzzy half: when the wording of the error varies, keyword lookup misses similar incidents that semantic search would find, and determinism is not worth missed matches.
  2. C is wrong because semantic search can return a similar-but-wrong incident for an ID query, which the constraint explicitly forbids.
Q8D3MediumSelect one
A team installs a community MCP server that gives their agent shell access. The server fetches its tool descriptions from a remote config file hosted by the server author. During testing, the agent suddenly tries to exfiltrate an API key after reading a tool description.
Constraint: the agent must be able to use third-party MCP servers without letting server content hijack its behavior.
What is the root cause, and the correct mitigation?
  1. Root cause: the model is too small. Mitigation: upgrade the model.
  2. Root cause: prompt injection through untrusted tool descriptions. Mitigation: treat MCP tool schemas as untrusted input, pin server versions, and sandbox or gate destructive tool calls behind confirmation.
  3. Root cause: the MCP protocol is insecure. Mitigation: stop using MCP and rewrite every tool by hand.
  4. Root cause: the API key was in the prompt. Mitigation: delete the key and continue.
Show answer and explanation
Answer: B

Why B is correct: tool descriptions are model input, so a malicious or compromised server can inject instructions through them. Pinning versions stops silent updates, treating schemas as untrusted blocks the injection path, and sandboxing plus confirmation gates limit what a hijacked call can do.

  1. A is wrong because model size does not fix prompt injection; larger models follow injected instructions just as well.
  2. C is wrong because the protocol is not the flaw; untrusted content is. Rewriting everything by hand throws away MCP's value without addressing the actual attack path.
  3. D is wrong because deleting the key after exfiltration does not stop the next attempt; it treats the symptom, not the injection.

Which integration approach fits?
  1. Have each team call the SDK directly from its own agent code.

Why B is correct: an MCP server built once gives every team the same clean tool interface while isolating the proprietary SDK in exactly one place. That is the build-once rationale: one integration to maintain, three consumers.

  2. C is wrong because agent-to-agent protocols connect agents to agents; the carrier exposes an SDK, not an agent.

Q78D3MediumSelect one
A finance agent was given 23 tools, including a raw SQL tool "for flexibility." Wrong-tool calls are rising: the model picks roughly similar tools, then retries, and once ran an unfiltered SELECT over the transactions table.
Constraint: keep every capability the agent needs, but cut wrong-tool calls and remove the dangerous flexibility.
What is the best fix?
  1. Upgrade to a larger model that can distinguish 23 tools more reliably.
  2. Consolidate into a few parameterized tools with narrow, well-named operations (for example, one reporting tool with explicit query types), and remove raw SQL entirely; review the catalog for overlap.

  1. A is wrong because tool-bloat is an architectural problem, not a capacity problem (bigger-model trap); a larger model still faces 23 similar choices.
  2. C is wrong because a recommender adds a 24th tool and another model judgment to the path that is already failing.

Q83D3MediumSelect one
A travel agent calls a partner airline API. The partner has degraded: responses now take 40 seconds. The agent waits, users time out, and the agent's retries pile more load onto the struggling partner.
Constraint: the agent must stay responsive even while the partner is slow, and must not make the partner's overload worse.
Which resilience design meets the constraint?
  1. Raise the retry budget and add exponential backoff so every request eventually succeeds.
  2. Set a short timeout, cap concurrent partner calls with a bulkhead, and trip a circuit breaker after repeated failures, serving a graceful fallback ("live prices unavailable, showing cached fares") instead of hanging.
  3. Queue all partner requests and process them serially to be gentle.
  4. Remove the timeout entirely so slow responses can complete.
Show answer and explanation
Answer: B

Why B is correct: timeouts bound the wait, the bulkhead caps how much of the agent the partner can consume, and the circuit breaker stops the retry pile-on; the fallback keeps the agent responsive. Each piece answers one half of the constraint.

  1. A is wrong because more retries against a degraded partner is a retry storm: it deepens the overload while users still wait (retry-storm trap).
  2. C is wrong because a serial queue turns 40-second responses into unbounded user-facing latency; gentleness to the partner is bought with the agent's responsiveness.
  3. D is wrong because no timeout means one slow partner can hang the agent's workers indefinitely.
Q84D3MediumSelect one
A billing agent listens for payment webhooks. The provider's docs warn that webhooks may be delivered more than once. Last month a duplicate delivery charged a customer twice, and the refund cost the company the customer.
Constraint: the charge must happen exactly once per triggering event, even if the webhook arrives five times.
Where and how should idempotency be enforced?
  1. In the agent's conversation memory: remember processed webhook IDs and skip repeats.
  2. At the payment service, keyed on the webhook's event ID: the service that performs the charge checks the key before charging, so duplicates are no-ops no matter how many times delivery repeats.
  3. Ask the customer to confirm before each charge, which catches duplicates.
  4. Deduplicate in the webhook receiver's in-memory cache.
Show answer and explanation
Answer: B

Why B is correct: idempotency must live at the effect-performing service, keyed on the triggering event's ID. The payment service is the only place that can guarantee exactly-once charging across restarts, retries, and duplicate deliveries.

  1. A is wrong because conversation memory is per-session and ephemeral; a restart or a second agent instance forgets it, and the double charge returns.
  2. C is wrong because customer confirmation is terrible UX and still racy: two deliveries can both be "confirmed."
  3. D is wrong because an in-memory cache dies with the process; durability is the whole point of idempotency.

Q9D3HardSelect one
A code-migration agent must work across a 2-million-line monorepo. The first design loaded a summary of every file into context at session start. Sessions now exceed the context window before the agent does any useful work, and costs have tripled.
Constraint: the agent must navigate the full repo without loading it all upfront, and per-session token cost must return to the original budget.
Which context strategy fixes this?
  1. Switch to a model with a 1-million-token context window and keep loading all summaries.
  2. Progressive discovery: give the agent search and file-reading tools plus an index of entry points, so it pulls only the code it needs, when it needs it.
  3. Compress all summaries with a smaller model before the session starts, then load the compressed version.
  4. Split the repo into 50 fixed partitions and run 50 agents, one per partition.
Show answer and explanation
Answer: B

Why B is correct: progressive discovery replaces the monolithic upfront load with on-demand retrieval. The agent starts from entry points and fetches only relevant files, which fits any repo size and brings token cost back down. This is the textbook fix for monolithic-context failure.

  1. A is wrong because a bigger window just delays the failure and costs more per token; it does not change the wasteful load-everything pattern.
  2. C is wrong because compression loses the details migration work depends on (exact APIs, edge cases), and it still front-loads cost for code never touched.
  3. D is wrong because 50 agents multiply cost and coordination overhead, and most partitions are irrelevant to any single migration task.

A hospital deploys a discharge-summary assistant that handles PHI (protected health information). Legal requires: patient data must not leave the hospital's approved AWS region, must not be used for model training, and every access must be auditable. The team considers the direct Anthropic API versus Anthropic models on AWS Bedrock.
Constraint: data residency pinned to the hospital's approved AWS region, no training on PHI, full auditability. All three are legal requirements, not preferences.
Which deployment choice satisfies all three?
  1. Direct Anthropic API with zero data retention (ZDR) enabled, plus application-level audit logs.
  2. AWS Bedrock in the hospital's region with PHI-eligible configuration, a signed BAA, inference logging to the hospital's own audit store, and no data leaving the region.
  3. Direct Anthropic API in the default configuration, since Anthropic never trains on API data by default.
  4. Self-host an open-weights model on hospital servers to avoid all third-party terms.
Show answer and explanation
Answer: B

Why B is correct: Bedrock keeps inference inside the chosen AWS region (residency), offers HIPAA-eligible services with a BAA (the legal instrument auditors require), and lets the hospital own the audit logs. It is the only option that structurally satisfies all three legal requirements.

  1. A is wrong because the direct API cannot pin processing and storage to a specific AWS region (inference is global or US-only, workspace storage is US-only), so it cannot satisfy the residency requirement. Q11D3HardSelect one
A company builds a RAG system over a mixed corpus: long PDF policy documents, relational tables of product specs, and a codebase. One engineer proposes a single chunking rule (500-token windows) and one dense vector index for everything.
Constraint: retrieval quality must stay high across all three content types. A query like "which products support feature X and what does the policy say about refunds" must work.
Why will the single-strategy proposal fail, and what should replace it?
  1. It will fail on cost. Replace it with a smaller embedding model.
  2. It will fail because different data shapes need different handling: chunk PDFs by section, index tables as structured rows with metadata filters, chunk code by function; use hybrid dense plus keyword search over the combined index.
  3. It will fail on latency. Replace it with an in-memory cache of all embeddings.
  4. It will not fail; uniform chunking is the industry best practice for mixed corpora.

Exam-Day Strategy

How to spend 120 minutes on 63 scenario items and walk out above 720.

1. The time math

time_per_item = total_minutes / item_count

Where: total_minutes = 120 (the exam length); item_count = 63 (the number of items). Worked: 120 / 63 = 1.90 minutes = 1 minute 54 seconds per item. The two-pass budget follows from the same numbers: 63 items x 90 seconds = 5,670 seconds = 94.5 minutes for pass one, leaving about 25 minutes for pass two.

  • 63 items in 120 minutes is 1 minute 54 seconds per item. Budget two passes: a first pass at about 90 seconds per item answering everything you can, then a second pass with the remaining time for flagged items.
  • Flag and move on the moment you catch yourself re-reading a scenario a third time. A stuck item costs you two easy items elsewhere.
  • Multiple-response items take longer. That is expected. Do not borrow their time from ten single-select items; borrow it from the second pass.

2. Read constraint-first, every item

  1. Find the constraint before the options. Scan the scenario for numbers and rules: the accuracy SLA, the latency budget, the cost ceiling, the regulation, the deadline. Underline them mentally.
  2. Predict the answer shape. Before reading option A, ask: "what would satisfy this constraint?" This inoculates you against attractive distractors.
  3. Judge each option against the constraint, not against general goodness. The exam's signature trap is an option that is good engineering but breaks the stated rule (the cheapest model that misses the SLA, the thorough review that misses the deadline).
  4. Watch for absolute words. "Never," "always," "every," and "no exceptions" in a scenario usually point to structural controls (filters, gates, contracts), not prompt wording.
The pattern behind most items:

two options are plausible and partially right. The credited one is the one that best satisfies every part of the constraint at once. When torn between two, re-read the constraint and ask which option leaves a piece of it unaddressed.

3. Multiple-response tactics

  • Treat each option as its own true/false question. Decide independently whether the option belongs, then check that your "true" count matches the required number.
  • Beware the overlap trap. Two options can both sound true while covering the same ground. Judge each option against the constraint, then pick the pair that covers it fully with no wasted overlap. In Q7, the router (D) already includes exact lookup for ID queries, so the winning pair is A (the fuzzy half) plus D (routing plus the exact half): complete coverage, zero overlap.
  • Beware the partial-credit trap. An option that is "mostly right but misses one constraint" is wrong. On this exam, partially satisfying the constraint is the most common distractor design.
  • If you are sure about one option and torn on the second, eliminate the ones that violate any constraint first. The field usually narrows to two.

4. Domain-weighted triage

  • No domain exceeds 19 percent and six of seven sit between 13 and 19 percent. There is no "skip this domain" play. The score report shows percent-correct per domain, so a collapsed domain can sink you.
  • D3 (Integration) is the largest at 19 percent: expect the most items on RAG design, MCP vs API vs agent-to-agent, tool bloat, and auth gaps.
  • D2 (Prompting) is only 13 percent and ranks 6th of 7. Do not over-invest in prompt trivia. The exam tests model selection trade-offs and context engineering, not clever prompt tricks.
  • D5 and D6 (Governance, Stakeholder) together are 28 percent and have no CCAR-F equivalent. If you are coming from the Foundations tier, these two domains deserve extra study time.

5. When you are stuck

  1. Re-read the constraint box, not the options. Half of all stuck moments resolve here: you were optimizing for the wrong thing.
  2. Ask "what would break in production?" The exam rewards the option that survives contact with reality: the control that works when the prompt is bypassed, the metric that catches the real failure, the SLA grounded in pilot data.
  3. Prefer structural answers over verbal ones. Filters beat prompt pleas. Contracts beat policies. Measured evals beat hoped-for improvements. When two options remain and one is structural, it is usually credited.
  4. Prefer the answer that addresses the whole scenario over the one that addresses half brilliantly.
  5. Never leave an item blank. There is no penalty for a wrong answer beyond the missed point, so a constraint-guided guess beats an empty one.

6. Common trap patterns in this bank (and on the exam)

  • The aggregate trap: overall metrics hiding per-segment failures. Always check per-type, per-category, per-position numbers (Q59, Q32).
  • The prompt-plea trap: "add it to the system prompt" as the safety or reliability fix. Prompts are bypassable; the credited answer is structural (Q34, Q36, Q28).
  • The bigger-model trap: upgrading the model as the fix for retrieval, chunking, tool-bloat, or grounding problems. The failure is architectural, not capacity (Q3, Q28, Q56).
  • The demo trap: judging by the happy path instead of measured coverage. Demos impress; eval sets decide (Q48).
  • The good-engineering trap: an option that is sensible in general but violates the specific constraint (cost, latency, regulation). Always re-check the constraint last.
  • The fan-out trap: parallelizing work that is actually sequential. Fan-out only helps independent subtasks; on a sequential dialogue it multiplies cost and fragments context (Q66).
  • The retry-storm trap: answering a degraded dependency with more retries instead of timeouts, bulkheads, and circuit breakers. Retries deepen the overload they are meant to survive (Q83).
  • The stale-eval trap: trusting evals drawn from an older production mix after the world changed. Green scores on last quarter's tickets say nothing about this quarter's traffic (Q86).
  • The BAA-scope trap: assuming one BAA covers every data flow the agent touches, or that any plan is BAA-eligible. Coverage is per-flow and per-plan, never ambient (Q95, Q96).
  • The sentiment trap: treating user love as evidence of task success. Applause measures feeling; only outcome metrics measure the job (Q101).
