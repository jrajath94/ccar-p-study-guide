Retrieval and RAG

TermMeaning
RAG (Retrieval-Augmented Generation)Answering from your own documents: the system retrieves relevant passages and the model answers from them, instead of answering from memory.
ChunkOne small retrievable piece of a document. Chunking is the decision of where to cut.
EmbeddingA long list of numbers that captures the meaning of a piece of text. Similar meanings land near each other.
VectorThe embedding stored as a point in a mathematical space, so the database can find "nearby" meanings fast.
MetadataFacts stored alongside a chunk, such as document ID, section, or date, used to filter before the similarity search.
Top-kThe k highest-scoring chunks returned by retrieval, for example the top 5.
RerankA second, slower model that re-scores the retrieved chunks and keeps only the best few. Cheap recall first, careful precision second.
Semantic searchSearching by meaning (embeddings), so "car" matches "automobile".
Keyword searchSearching by exact words (such as BM25, a classic word-frequency ranking formula), so "car" does not match "automobile".
Hybrid searchRunning semantic and keyword search together and merging the results, to catch both meaning and exact terms.
PrecisionOf the chunks retrieved, how many were actually relevant.
RecallOf all the relevant chunks that exist, how many the retrieval found.
FaithfulnessThe share of the answer's claims that are verifiable against the retrieved text. The opposite of hallucination.
HallucinationThe model stating something as fact that is not supported by its sources.
ROUGEA score that measures word overlap between a generated summary and a reference summary. It rewards similar wording, not truthfulness.

How to read this diagram
  1. We chunk docs into 500-1000 token pieces. These pieces have 10-20% overlap. Then we embed them as fixed-dimension vectors.
  2. The vector DB indexes them for approximate nearest-neighbor search.
  3. Hybrid adds BM25 lexical search; fusion combines both rankings.
  4. Rerank scores query and document together with a cross-encoder and keeps the top-k.
  5. The exam never asks for one number: it asks you to argue the trade-off. Bigger chunks raise recall but also noise and cost.

What breaks if a part fails: If the chunking ignores the data shape, recall dies no matter how good the reranker is.

Models and context

TermMeaning
TemperatureA setting that controls randomness: low temperature makes the model pick the most likely token each time, high temperature makes it sample more freely.
Context windowThe maximum amount of text (prompt plus history plus retrieved chunks) the model can consider in one request.
Zero-shotAsking the model to do a task with instructions only, no examples.
Few-shotShowing the model a few worked examples inside the prompt before asking it to do the task.
Chain-of-thoughtAsking the model to reason step by step before giving the final answer, which usually improves accuracy on hard problems.
Prompt cachingYou pay full price one time for the stable part of a prompt. Then you pay a tenth of the price. This occurs when you reuse the same prefix within a few minutes.
LLM judgeUsing a language model, guided by a scoring rubric, to grade another model's outputs at a scale humans cannot match.
Golden setThis is a frozen, versioned collection of test cases. It has known-good answers. We score every change against this collection.

Integration and reliability

TermMeaning
MCP (Model Context Protocol)The open standard that connects Claude to external tools and data through small services called MCP servers.
OAuth 2.0This is the industry standard for delegated sign-in. The user logs in one time. The service receives a narrowly scoped token. It does not receive a shared password or API key.
SSO (single sign-on)One login that grants access to many company systems, managed centrally by IT.
SandboxAn isolated execution environment where untrusted code or tools can run without touching real systems.
TimeoutA maximum wait: if the tool or model call takes longer, it is cut off and treated as failed.
RetryCalling again after a failure. Safe only for idempotent operations (ones where running twice has the same effect as running once).
Circuit breakerA guard that stops calling a failing service for a while, so retries do not pile onto an outage.
BulkheadA cap on how many calls can hit one dependency at once, so one slow partner cannot consume every worker.
Rate limitA cap on how many requests a caller may make in a time window.
CanaryReleasing a change to a small slice of traffic first and watching the metrics before rolling it out fully.
RollbackReverting to the previous working version when a release misbehaves.

Measurement

TermMeaning
SLA (service-level agreement)A promised target, such as "95 percent accuracy" or "answer within 2 seconds", that the design must meet.
p95 latencyThe latency that 95 percent of requests beat. If p95 is 2 seconds, 5 percent of users wait longer.
LatencyHow long one request takes, end to end.
ThroughputHow many requests the system handles per unit of time.
A/B testRouting part of the traffic to version A and part to version B, then comparing measured outcomes to decide which ships.

How to read this diagram
  1. p50 is the median ticket: 1.8s. p95 is the 95th percentile: 4.6s. p99 is 9.2s.
  2. The dashed SLA line is at 5 seconds. This line shows your performance target. Tickets above this line fail.
  3. Kill outliers before optimizing the median: p95 falls faster from the right tail than from the middle.
  4. Prompt design levers for latency: cap max_tokens, fix the output format, use stop sequences.

What breaks if a part fails: If you optimize the median, the SLA can still fail. The users in the tail are the ones who complain.

Governance and safety

TermMeaning
PII (personally identifiable information)Data that identifies a person: names, emails, phone numbers, addresses, account numbers.
PHI (protected health information)Health data covered by HIPAA: diagnoses, visit notes, prescriptions, anything tying health facts to a patient.
GDPRThis is the European privacy regulation. It controls how to collect personal data. It controls how to store personal data. It controls how to process personal data of EU residents.
HIPAAThe US health-privacy law. Processing PHI requires a signed BAA with the vendor.
FedRAMPThe US federal program that authorizes cloud services to handle government data, with graded impact levels.
BAA (Business Associate Agreement)The contract a vendor signs promising to safeguard PHI. Only certain plans and surfaces are BAA-eligible.
ZDR (zero data retention)A contractual promise that the provider stores none of your request or response data after serving it.
Data retentionHow long a provider keeps your prompts and outputs, and under what terms.
Human-in-the-loop (HITL)A design where the system pauses and a person approves before a sensitive or irreversible action proceeds.
Red teamA group that attacks the system on purpose (jailbreak attempts, injection, misuse) to find weaknesses before real attackers do.
JailbreakA prompt crafted to make the model bypass its own safety rules.

Why this order. The bank follows exam weight. The heaviest domain is first. Your practice time matches where the points are. D3 Integration is 19 percent of the exam. This is the largest single share.

It is also the most scenario-dense. It includes tool and agent configuration, auth gaps, accuracy-latency trade-offs, observability, RAG pipelines, and MCP versus API, CLI, and agent-to-agent patterns.

How to read this diagram
  1. PREVENT: deny before the model acts. Least-privilege scopes, zero-data-retention, policy denial.
  2. DETECT: see the leak while it happens. PreToolUse hooks, PII scanners, audit logs.
  3. RESPOND: contain the blast radius. Kill switch, revoke the key, run the incident runbook.
  4. GOVERN: prove it afterward. Deletion certificates, audit trails, reviews. GDPR wants data minimization and deletion, HIPAA wants PHI access controls and audit trails, FedRAMP wants accredited infrastructure.

What breaks if a part fails: If governance is only a policy document, there is no evidence when the auditor asks. Compliance evidence is a deliverable.

D4. Evaluation, Testing and Optimization (16% of the exam, about 10 items)

Why this comes next. D1 decided what to build and D3 connected it. D4 asks the question neither answered: how do you know it works? Evaluation design, testing strategy, and optimization under constraints. Sixteen percent of the exam.

How to read this diagram
  1. Start with the rubric: the judge criteria written down before anything runs.
  2. Build the golden set: 50-200 query and answer pairs with known-good answers.
  3. Run the harness on the same prompt every time, diff the failures, cluster the causes.
  4. Fix one thing, then let CI gates block the merge if a gate fails.
  5. The loop never ends: every failure the loop cannot catch becomes a new fixture.

Q1D3EasySelect one
A legal-tech startup builds a contract assistant. The assistant answers questions about 40,000 vendor contracts. Users ask questions like "What is the termination notice period in contract ACME-2024-118?". Users expect the exact clause quoted. The team designs the RAG pipeline. The team must choose a chunking strategy.
Constraint: answers must cite the exact clause. Small errors in clause text are unacceptable to the legal team.
Which chunking strategy best satisfies the constraint?
  1. Split each contract into 2,000-token chunks with no overlap, to keep each clause in rich surrounding context.
  2. Split each contract into 400 to 600-token chunks with 10 percent overlap, and attach contract ID plus section heading as metadata on every chunk.
  3. Embed each full contract as a single vector and retrieve the whole contract, letting the model find the clause.
  4. Chunk by fixed 100-token windows with no overlap or metadata, to maximize retrieval precision.
Show answer and explanation
Answer: B

Why B is correct: The constraint is exact clause citation. Small chunks raise retrieval precision. This ensures the cited clause is actually returned. Overlap prevents clauses split across boundaries from being lost. Metadata (contract ID, section) lets the system filter and cite correctly.

  1. A is wrong. 2,000-token chunks dilute precision. The retriever returns long passages. The model may quote the wrong clause from the same chunk.
  2. C is wrong. A whole contract far exceeds useful retrieval granularity. The model cannot reliably locate one clause in 40,000 embedded documents.
  3. D is wrong. 100-token windows with no overlap will slice clauses in half. Without metadata, the system cannot attribute a quote to the right contract.
Q2D3EasySelect one
A sales team wants a Claude agent that can look up accounts and update opportunities in their CRM. The CRM exposes a stable, well-documented REST API with six endpoints. One engineer proposes building an MCP (Model Context Protocol) server; another proposes calling the REST API directly through function calling.
Constraint: ship in two weeks with the smallest maintenance surface. Only this one CRM is in scope.
Which integration approach should the architect choose?
  1. Call the CRM REST API directly through function calling, since there is one stable API and six endpoints.
  2. Build both an MCP server and direct REST tools, so the agent can choose at runtime.
  3. Use an agent-to-agent protocol so the CRM can negotiate with the Claude agent directly.
  4. Build an MCP server. MCP is the standard. Future tools will need MCP.
Show answer and explanation
Answer: A

Why A is correct: MCP pays off when there are many tools. It also pays off with dynamic discovery or shared servers across agents. With one stable API and a two-week deadline, direct function calling is simpler. It has less to maintain. This is exactly what the constraint asks for.

  1. D is wrong. "MCP is the standard" is not a reason by itself. It adds a server to build, host, and secure. There is no capability gain here.
  2. B is wrong. Maintaining two integration paths doubles the maintenance surface. This is the opposite of the constraint.
  3. C is wrong. Agent-to-agent protocols connect agents to agents. They do not connect agents to a REST API. The CRM is not an agent.
Q3D3EasySelect one
A support agent got 47 tools. Every internal API got its own function. After launch, the team sees slow responses. The team sees frequent wrong-tool calls. The model often picks a similar tool. The model picks the wrong tool.
Then the model retries.
Constraint: reduce wrong-tool calls without removing any capability the agent needs.
What is the best fix?
  1. Upgrade to a larger model so it can handle 47 tools more reliably.
  2. Add five more helper tools that pre-select the right tool for common cases.
  3. Group tools into fewer, well-named functions (or namespaced MCP servers) so the agent sees a small set of distinct choices, with details revealed on demand.
  4. Raise the temperature so the agent explores different tools more creatively.
Show answer and explanation
Answer: C

Why C is correct: This is tool bloat. A flat list of 47 similar tools makes selection a guessing game. Grouping into a small set of distinct, well-named entry points cuts wrong-tool calls. It also keeps every capability reachable. This is progressive disclosure of the rest.

  1. A is wrong. A larger model costs more. It also adds latency. It treats the symptom (bad selection) instead of the cause (47 indistinguishable options).
  2. B is wrong. Adding tools makes the bloat worse. It does not make it better.
  3. D is wrong. Higher temperature increases randomness. This increases wrong-tool calls.
Q4D3EasySelect one
An internal Claude agent reads and files expense reports through the finance API. It authenticates with a single shared service token that has full read and write access to every employee's expenses. A security review flags this before launch.
Constraint: the agent must act only within the requesting employee's own permissions. No shared privileged credential.
Which auth design resolves the finding?
  1. Remove authentication entirely and rely on the office VPN for access control.
  2. Keep the shared token but rotate it weekly.
  3. Give the agent one token per employee, all with full admin scope, stored in the agent's config file.
  4. Use OAuth 2.0 delegated tokens: each request carries the requesting user's own token, scoped to least privilege.
Show answer and explanation
Answer: D

Why D is correct: OAuth delegated tokens make the agent act as the user. The agent has only that user's permissions. This satisfies the least privilege principle. This removes the shared privileged credential.

  1. B is wrong. Rotation does not change the blast radius. One leaked token still reaches everyone's expenses.
  2. C is wrong. Per-employee admin tokens are still over-privileged. Storing them in a config file creates a new secret-sprawl problem.
  3. A is wrong. The VPN proves network location. It does not prove user identity or authorization. Any user on the VPN can reach anyone's expenses.
Q5D3MediumSelect one
A chat triage agent classifies incoming support tickets. The current design uses a large model with long chain-of-thought reasoning: accuracy is 93 percent, but p95 latency is 6 seconds. The product requirement is p95 latency under 2 seconds with accuracy at or above 90 percent. Ticket volume is 300,000 per month.
Constraint: p95 under 2 seconds AND accuracy at or above 90 percent. Both must hold at 300K tickets per month.
Which design best meets both bars?
  1. Route with a fast model first; escalate to the large model only when the fast model's confidence is low. Verify the mix on a labeled eval set.
  2. Cache every ticket classification so repeat tickets never hit the model.
  3. Switch everything to the smallest, fastest model and accept whatever accuracy results.
  4. Keep the large model but cut the output token limit in half to reduce latency.
Show answer and explanation
Answer: A

Why A is correct: Tiered routing gets most tickets under the latency bar. A fast model runs first. The system escalates tickets with low confidence. A large model protects the accuracy bar on hard cases. The eval-set check proves both bars hold before launch. This meets the constraint.

  1. C is wrong. It guarantees the latency bar. It abandons the accuracy bar. "Accept whatever accuracy" violates the stated 90 percent floor.
  2. D is wrong. Cutting output tokens does not reliably cut 6 seconds to under 2 seconds. It risks truncating the reasoning. The 93 percent accuracy depends on this reasoning.
  3. B is wrong. Support tickets are mostly unique. Cache hit rates will be near zero. This changes almost nothing.
Q6D3MediumSelect one
A production assistant handles 2 million requests per day across search, summarization, and tool calls. The team wants to detect quality drift, especially hallucinations, within one day of it starting. Today they only log the final user-facing text.
Constraint: detect hallucination drift within 24 hours at 2M requests per day, without storing every full prompt and completion (too expensive).
Which observability strategy fits?
  1. Emit structured traces (one span per tool call and model call with token counts and latency), sample a fraction of full transcripts, and run an automated faithfulness eval over the sample daily.
  2. Track only aggregate latency and token cost dashboards.
  3. Log only error responses and review them weekly.
  4. Store every prompt and completion in full, and hire reviewers to read them.
Show answer and explanation
Answer: A

Why A is correct: Structured traces give cheap, always-on coverage of behavior. Sampling keeps storage affordable at 2M requests per day. A daily automated faithfulness evaluation on the sample detects hallucination drift. This happens inside the 24-hour window.

  1. C is wrong. Hallucinations rarely raise errors. Error logs miss them entirely. Weekly review misses the 24-hour window.
  2. D is wrong. Full logging at 2M requests per day violates the cost constraint. Manual review cannot keep up.
  3. B is wrong. Latency and cost dashboards say nothing about answer quality. Drift would be invisible.
Q7D3MediumSelect two
An IT helpdesk agent handles two query patterns. Pattern (1): "find the three most similar past incidents to this error message" (fuzzy, wording varies). Pattern (2): "what is the status of incident INC-48210" (exact lookup by ID). The team now chooses a retrieval strategy over the incident database.
Constraint: both query patterns must return correct results. Fuzzy queries need semantic matching; exact queries must never return a "similar but wrong" incident.
Which two approaches together satisfy the constraint? (Select two.)
  1. Use dense vector search for both patterns, trusting the embedding to rank INC-48210 first.
  2. Route the query first: detect an incident ID pattern and send it to exact lookup, otherwise use semantic search.
  3. Use dense vector (semantic) search for the fuzzy similar-incident queries.
  4. Use exact keyword matching on the full error text for the fuzzy similar-incident queries, so results stay deterministic.
Show answer and explanation
Answer: C, B

Why C, B is correct: The constraint has two halves. C supplies the correct mechanism for the fuzzy half. This is dense semantic search. B supplies the routing rule. Detect an incident ID and send it to exact lookup. Otherwise, use semantic search.

Together they cover both query patterns. They use the correct mechanism each time.

  1. D is wrong. Exact keyword matching cannot handle the fuzzy half. If the wording of the error varies, keyword lookup misses similar incidents. Semantic search would find these incidents. Determinism is not worth missed matches.
  2. A is wrong. Semantic search can return a similar-but-wrong incident for an ID query. The constraint explicitly forbids this.
Q8D3MediumSelect one
A team installs a community MCP server that gives their agent shell access. The server fetches its tool descriptions from a remote config file hosted by the server author. During testing, the agent suddenly tries to exfiltrate an API key after reading a tool description.
Constraint: the agent must be able to use third-party MCP servers without letting server content hijack its behavior.
What is the root cause, and the correct mitigation?
  1. Root cause: prompt injection through untrusted tool descriptions. Mitigation: treat MCP tool schemas as untrusted input, pin server versions, and sandbox or gate destructive tool calls behind confirmation.

Engineering wants to ship the new triage agent Friday. The risk team says eval coverage on the known-hard tail is thin and wants two more weeks of evals. Both sides have reasonable arguments and the deadline is real.
Constraint: the decision must be defensible either way, with the trade-off owned and recorded.
What is the architect's role here?
  1. Escalate to the CTO without a recommendation so leadership owns it.
  2. Own the trade-off: quantify the residual risk, document the decision and its rationale in writing (ship with a scoped rollout plus monitoring, or delay with specific eval gates), and get sign-off from both sides.
  3. Ship Friday and promise the risk team that evals will catch up later.
  4. Let the two sides argue it out and go with whoever argues best.
Show answer and explanation
Answer: B

Why B is correct: The architect owns the trade-off. Quantifying residual risk makes the outcome defensible. Recording the decision with its rationale makes the outcome defensible. A scoped rollout turns the disagreement into a plan. Specific evaluation gates turn the disagreement into a plan. Both sides signed this plan.

  1. D is wrong. The best arguer is not the best decider. Rhetorical victory leaves the trade-off unowned. It leaves it unrecorded.
  2. A is wrong. Escalation without a recommendation means the architect gives up the job. Leadership gets a conflict. It does not get an analysis.
  3. C is wrong. Shipping on a promise of later evaluations takes the risk team's concern. It schedules it for never.
Q101D6MediumSelect one
A pilot of a drafting agent ends with glowing user feedback: "love it," "so fast," five-star ratings. But the task metric, drafts accepted without heavy edits, sits flat at 61%, unchanged from the old tool.
Constraint: the scale decision must rest on evidence the agent does the job, not on how it feels.
Should the team scale the pilot?
  1. Scale it but keep the old tool as backup, which hedges the decision.
  2. Ask users to rate it again in a month for a larger sample.
  3. Yes; users love it, and sentiment is the ultimate metric.
  4. Not yet: investigate why love does not convert into accepted drafts (novelty effect, politeness bias, speed mistaken for quality), and scale only when the outcome metric moves.
Show answer and explanation
Answer: D

Why D is correct: Sentiment measures feeling. The outcome metric measures the job. If they diverge, the scale decision follows the outcome metric. The gap itself is the investigation. Glowing ratings over flat results usually mean novelty. They can also mean politeness.

They do not mean value.

  1. C is wrong. Sentiment without outcome movement is applause. It is not evidence (sentiment trap). Scaling on applause buys licenses. It does not buy results.
  2. A is wrong. Keeping the old tool hedges operations. It does not hedge the decision. It scales the cost. The evidence question stays open.
  3. B is wrong. A larger sample of the same sentiment metric still measures feeling. It does not measure accepted drafts.
Q102D6MediumSelect one
A deprecation notice arrives. The vendor will retire the pinned model version in 90 days. This version supports 14 production workloads. All 14 workloads use one pinned version. This version is in a shared configuration. All workloads must move together.
Constraint: migrate within 90 days with no flag-day cutover and no untested workload going live on the new model.
Which migration design fits?
  1. Move all 14 workloads to the new model on the same day and watch the dashboards.
  2. Give each workload its own model pin. Put the pin behind an abstraction layer. Migrate workloads one by one. Re-run evaluations for each workload. Keep the old pin available. Keep it available until the last workload clears.
  3. Pin every workload to "latest" so deprecations never matter again.
  4. Ask the provider for an extension and hope the problem goes away.
Show answer and explanation
Answer: B

Why B is correct: The shared pin is the coupling. It forces a flag day. Per-workload pins decouple the migration. Each workload moves when its own evaluations pass. The old version stays live for stragglers. There is no big bang.

There is no untested cutover.

  1. A is wrong. A same-day cutover of 14 workloads is a flag day. One bad workload stops all 14 workloads. The constraint bans this.
  2. C is wrong. "Latest" trades deprecation risk for uncontrolled change. Every provider update becomes a silent migration.
  3. D is wrong. An extension moves the deadline. It does not fix the coupling. The next notice brings the same flag day.
Q103D7EasySelect one
A 200-person engineering org adopts Claude Code. Each engineer configures their own settings. Security needs permissionless mode disabled for repositories holding export-controlled code, and the setting must actually hold.
Constraint: the control must be enforceable against individual override, not advisory.
Which settings layer provides that?
  1. A policy memo asking engineers to disable permissionless mode on sensitive repos.
  2. Managed settings pinned at the org level, which enforce authority in a way individual configuration cannot override.
  3. A well-written repository CLAUDE.md instructing the agent to ask before acting.
  4. Per-user settings, since every engineer already has them.
Show answer and explanation
Answer: B

Why B is correct: The platform enforces only managed settings. It enforces them against individual override. Per-user settings, memos, and repo files are all advisory. They ask. They do not enforce.

  1. D is wrong. The user controls per-user settings. They cannot constrain the user.
  2. A is wrong. A memo relies on compliance. It enforces nothing technically.
  3. C is wrong. CLAUDE.md shapes the agent's intent. It is not an enforcement layer.
Q104D7MediumSelect one
A team shares one Anthropic API key across all CI jobs in every environment. A contractor's laptop had the key in shell history last week, and nobody can say which jobs used it.
Constraint: the blast radius of any single key leak must be small, and key usage must be attributable.
What is the right key hygiene?
  1. Issue scoped keys for each environment. Give each job the minimum permissions. Rotate the keys on a schedule. Revoke the shared key. Do not let one key span environments.
  2. Store the shared key in a nicer secrets manager and keep sharing it.
  3. Give every engineer their own copy of the shared key for local debugging.
  4. Keep the shared key but rotate it monthly.
Show answer and explanation
Answer: A

Why A is correct: Scoping bounds what a leaked key can do. Per-environment keys bound where the damage lands. Rotation plus revocation bound how long a leak matters. Attribution comes free when each environment has its own key.

  1. D is wrong. Monthly rotation of a shared key still gives one key access to everything between rotations. The blast radius does not get smaller.
  2. B is wrong. A secrets manager protects the key at rest. It does not change that one key is valid everywhere.
  3. C is wrong. More copies of a shared key increase the leak surface. This is the opposite of good hygiene.
Q105D7MediumSelect one
Debugging a production agent takes hours. The on-call engineer greps across model-call logs, tool logs, and app logs, trying to reconstruct which tool call belonged to which user request. Traces have no request IDs; tool results are free-text blobs.
Constraint: cut mean time to diagnose by making any production trace reconstructable in minutes.
What is the highest-leverage investment?
  1. Make observability a first-class build. Propagate correlation IDs across model calls. Propagate request IDs across model calls. Propagate correlation IDs across tools and services. Propagate request IDs across tools and services. Use structured tool inputs.
    Use structured tool outputs. One trace view reconstructs a request end to end.
  2. Upgrade to a larger model so there are fewer confusing behaviors to debug.
  3. Have the agent narrate its reasoning into the logs for every step.
  4. Log more: increase verbosity on every component.
Show answer and explanation
Answer: A

Why A is correct: Diagnosis is correlation. More logs are just more hay without shared IDs and structured results. Propagated request IDs and structured tool I/O change hours of grep into one trace lookup.

  1. D is wrong. Verbosity without correlation increases the haystack. The engineer already has too many logs.
  2. B is wrong. Model size does not fix untraceable systems. You can debug confusing behavior with IDs. You cannot debug clear behavior without IDs.
  3. C is wrong. Narration adds subjective text to unstructured blobs. It does not give the deterministic correlation that a trace needs.

How should the team package these workflows?
  1. Delete the wiki so nobody copies stale prompts.
  2. Keep the wiki but add "last updated" dates to each prompt.
  3. Package the recurring workflows as versioned Skills in the repo: reviewed, tested, and updated alongside the code they operate on. The wiki keeps prose; executable workflows live in version control.
  4. Email the current prompts to the team every Monday.
Show answer and explanation
Answer: C

Why C is correct: Recurring workflows earn versioning, review, and co-location with code. This makes them a maintained source of truth. It is not folklore. Skills are the packaging. The wiki was never version control.

Exam-Day Strategy

How to spend 120 minutes on 63 scenario items and walk out above 720.

1. The time math

time_per_item = total_minutes / item_count

Here are the values: total_minutes = 120 (the exam length). item_count = 63 (the number of items). Calculation: 120 / 63 = 1.90 minutes = 1 minute 54 seconds per item. The two-pass budget uses the same numbers. 63 items x 90 seconds = 5,670 seconds = 94.5 minutes for pass one. This leaves about 25 minutes for pass two.

  • 63 items in 120 minutes means 1 minute 54 seconds per item. Budget two passes. Complete a first pass at about 90 seconds per item. Answer everything you can. Then complete a second pass with the remaining time for flagged items.
  • Flag and move on the moment you catch yourself re-reading a scenario a third time. A stuck item costs you two easy items elsewhere.
  • Multiple-response items take more time. This is normal. Do not take time from ten single-select items. Take time from the second pass.

2. Read constraint-first, every item

How to read this diagram
  1. Scenario: read the story - who, what, which system.
  2. Constraint: find the rule - "must never", "at 2am", "even if...".
  3. Ask: name what the question really wants.
  4. Options: eliminate against the constraint.
  5. The constraint is the scoring key. Several options will be partly correct; the credited answer best satisfies the stated constraint.

What breaks if a part fails: if you read the options first, the attractive wrong option anchors you - the trap is built to feel right.

  1. Find the constraint before the options. Scan the scenario for numbers and rules: the accuracy SLA, the latency budget, the cost ceiling, the regulation, the deadline. Underline them mentally.
  2. Predict the answer shape. Before reading option A, ask: "what would satisfy this constraint?" This inoculates you against attractive distractors.
  3. Judge each option against the constraint, not against general goodness. The exam's signature trap is an option that is good engineering but breaks the stated rule (the cheapest model that misses the SLA, the thorough review that misses the deadline).
  4. Watch for absolute words. "Never," "always," "every," and "no exceptions" in a scenario usually point to structural controls (filters, gates, contracts), not prompt wording.
The pattern behind most items:

two options are plausible and partially right. The credited one is the one that best satisfies every part of the constraint at once. When torn between two, re-read the constraint and ask which option leaves a piece of it unaddressed.

3. Multiple-response tactics

  • Treat each option as its own true/false question. Decide independently whether the option belongs, then check that your "true" count matches the required number.
  • Beware of the overlap trap. Two options can both seem true. They can also cover the same ground. Judge each option against the constraint. Then pick the pair that covers it fully with no wasted overlap. In Q7, the router (B) already includes exact lookup for ID queries.
    So the correct pair is C (the fuzzy half) plus B (routing plus the exact half). This gives complete coverage and zero overlap.
  • Beware the partial-credit trap. An option that is "mostly right but misses one constraint" is wrong. On this exam, partially satisfying the constraint is the most common distractor design.
  • If you are sure about one option and torn on the second, eliminate the ones that violate any constraint first. The field usually narrows to two.

4. Domain-weighted triage

How to read this diagram
  1. Heavy (16-19%): D3, D1, D4. Deep passes here.
  2. Medium (13-14%): D5, D6, D2. Solid coverage.
  3. Light (7%): D7. Cheap points from scenarios you already know.
  4. Triage is a strategy, not a shortcut: cover everything, weight your effort.

What breaks if a part fails: if you skip D7 entirely, you donate four easy items - light does not mean zero.

How to read this diagram
  1. The longest bar is D3 Integration at 19%: about 12 of 63 items. Start there.
  2. D1, D4 follow at 17% and 16%. These three domains are half the exam.
  3. D7 is 7%: real points, but one hour on D3 buys more than one hour on D7.

What breaks if a part fails: if you study every domain equally, you over-invest where the fewest items live.

  • No domain exceeds 19 percent and six of seven sit between 13 and 19 percent. There is no "skip this domain" play. The score report shows percent-correct per domain, so a collapsed domain can sink you.
  • D3 (Integration) is the largest at 19 percent: expect the most items on RAG design, MCP vs API vs agent-to-agent, tool bloat, and auth gaps.
  • D2 (Prompting) is only 13 percent and ranks 6th of 7. Do not over-invest in prompt trivia. The exam tests model selection trade-offs and context engineering, not clever prompt tricks.
  • D5 and D6 (Governance, Stakeholder) together are 28 percent. They have no CCAR-F equivalent. If you come from the Foundations tier, these two domains need extra study time.

5. When you are stuck

How to read this diagram
  1. Re-read the constraint box. Do not re-read the options. Half of stuck moments resolve here.
  2. Name what you optimized for. You were probably optimizing for the wrong thing.
  3. Eliminate two distractors. Find the trap pattern. Two confident eliminations beat one shaky pick.
  4. Guess and flag, move on. No negative marking. Never leave it blank.

What breaks if a part fails: if you freeze on one item, you steal time from items you would have gotten right.

  1. Read the constraint box again. Do not read the options. Half of all stuck moments resolve here. You optimize for the wrong thing.
  2. Ask "what would break in production?" The exam rewards the option that works in reality. This is the control that works when someone bypasses the prompt. This is the metric that catches the real failure. This is the SLA based on pilot data.
  3. Prefer structural answers over verbal ones. Filters beat prompt pleas. Contracts beat policies. Measured evals beat hoped-for improvements. When two options remain and one is structural, it is usually credited.
  4. Prefer the answer that addresses the whole scenario over the one that addresses half brilliantly.
  5. Never leave an item blank. There is no penalty for a wrong answer beyond the missed point, so a constraint-guided guess beats an empty one.

6. Common trap patterns in this bank (and on the exam)

  • The aggregate trap: overall metrics hiding per-segment failures. Always check per-type, per-category, per-position numbers (Q59, Q32).
  • The prompt-plea trap: "add it to the system prompt" as the safety or reliability fix. Prompts are bypassable; the credited answer is structural (Q34, Q36, Q28).
  • The bigger-model trap: upgrading the model as the fix for retrieval, chunking, tool-bloat, or grounding problems. The failure is architectural, not capacity (Q3, Q28, Q56).
  • The demo trap: judging by the happy path instead of measured coverage. Demos impress; eval sets decide (Q48).
  • The good-engineering trap: an option that is sensible in general but violates the specific constraint (cost, latency, regulation). Always re-check the constraint last.
  • The fan-out trap: parallelizing work that is actually sequential. Fan-out only helps independent subtasks; on a sequential dialogue it multiplies cost and fragments context (Q66).
  • The retry-storm trap: answering a degraded dependency with more retries instead of timeouts, bulkheads, and circuit breakers. Retries deepen the overload they are meant to survive (Q83).
  • The stale-eval trap: trusting evals drawn from an older production mix after the world changed. Green scores on last quarter's tickets say nothing about this quarter's traffic (Q86).
  • The BAA-scope trap: assuming one BAA covers every data flow the agent touches, or that any plan is BAA-eligible. Coverage is per-flow and per-plan, never ambient (Q95, Q96).
  • The sentiment trap: treating user love as evidence of task success. Applause measures feeling; only outcome metrics measure the job (Q101).
